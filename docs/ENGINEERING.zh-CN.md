## 工程问题

### 斜杠入口去重（2026-10-05，待优化）

用户反馈安装 0.9.3 后，菜单中出现 `GenPet` 与 `genpet` 两组入口。当前安装清单只有一个 `genpet@genpet` 0.9.3，用户级旧 GenPet 技能已清空；配置中分别存在插件显示名 `GenPet` 和技能名 `genpet`，但尚未实际核实这两组菜单的来源。

用户确认的优化方向：skill 已能自动出现在斜杠菜单中，无需专门配置重复的斜杠命令。后续先核实插件入口与技能入口的实际关系，移除可避免的重复入口；保留各技能的明确调用方式，并在新聊天中检查菜单是否清晰、同一功能是否只有一个命令入口。本次只记录，不修改插件。

### 定时任务文案与机制分离（2026-10-05，待优化）

用户反馈本聊天定时任务的文案不符合产品原则：用户能够直接看到的文字，应作为用户体验的一部分来写。这个边界也适用于任务名称与可见任务说明、对话过程消息、通知和最终故事，不能只要求最终回复有体验。

后续将个体 ID 核对、周期与触发去重、未完成工作续接、成长兜底、素材审核、宿主更新和选择保留等执行要求，放入任务在后台读取的 skill、共享 workflow 或机制文档。可见文案表达宠物与用户的关系、会带来的经历及必要的用户选择；避免展示工程操作清单，也避免反复发送没有新内容的过程占位文字。机制必须仍能被实际读取并执行，不能仅从可见文案中删掉。

后续修改时同时检查用户能看到的任务文案与实际运行输出，确认体验表达自然、机制细节不外露，且原有绑定、续接和审核规则仍然有效。本次只记录，不改现有定时任务、插件或宠物。

用户补充（2026-10-05，成长确认文案）：确认后的技能条款解释没有必要，也违反用户可见文案的体验原则。必要的确认提问可以保留，只需在宠物世界里清楚表达将发生的变化，例如「要现在让它提前长成少年，换上新的模样吗？」；不要附带技能名称、规则引用、英文原句或为什么需要再次确认的执行说明。确认机制与依据放入后台读取的文档，后续同时调整技能与输出约束，避免确认后又泄露机制。本次仅记录待修改，不执行成长。

### 无新用户经历时的定时表达（2026-10-06，待讨论）

用户提出先记录，后续讨论：即使没有发生新的用户经历，定时检查应该触发什么样的文案。此处区分新的用户事实与宠物自己的故事；缺少用户新资料，不直接等同于宠物没有可表达的内容。

当前实测背景：2026-10-06 06:12、11:12 左右的两次检查分别使用 period:3、period:4，判断无值得新增的故事且成长兜底未到期，记录依据后取消当次故事，没有推送故事正文或图片。但对话仍出现「我会查看它的近况」这类过程提示，不符合无新内容时保持安静和机制隐藏的既有原则。

后续讨论内容：没有新用户事件时是否保持安静，或在合适时机表达宠物自己的生活、简短问候或已有经历的延续；表达应在什么条件和时机出现、是否需要图片、怎样避免每次检查都发送占位文字或重复故事。以上仅是讨论范围，不是已确定的分类、频率或固定台词。

继续遵守已确认的文案边界：用户可见内容有体验、来自宠物世界，不编造用户行为或情绪，不用工程状态报告填补空白。当前仅记录待讨论问题，不修改定时任务、运行规则或宠物记录，也不默认以后每次检查都推送。

### 同一图片重复展示（2026-10-06，待修复）

用户反馈查看当前宠物家的结果中，同一张家景出现两次。图像生成工具已自动展示生成结果，最终回复又通过绝对路径 Markdown 嵌入该图；把同一图从生成目录复制到个体素材目录，不会使其成为另一张图片。审图预览也应纳入展示检查，避免作为用户内容重复出现。

后续修复方向：协调图像工具、审图预览与 output 的展示方式；工具已经展示最终采用的图片时，最终回复只呈现配套故事文字，不再次嵌图；尚未展示时再呈现已验收图片。内部仍保留审核、持久素材与 mediaRefs，不因去重省略验收或把候选图当成已接受结果。核对应依据实际图像内容和已发生的展示，而非仅比较保存路径。

本次仅记录问题和修复方向，待后续修改插件提示词或输出流程；尚未发布修复版本。

### 领养及后续故事的用户关联不足（2026-10-06，待讨论修复）

用户反馈：目前宠物故事没有充分体现与用户的关联，最早领养蛋的故事也存在这个问题。设计目标是通过宠物故事建立宠物与用户之间的联系；当前体验尚未达到这一目标。用户要求先记录，后续讨论修复。

本次样本包括领养蛋、孵化与成长，以及结识小甲虫、树枝小乐队和参观家的后续故事。领养依据主要引用环境清理和入口简化等插件操作，最近的内容更多围绕宠物自己的生活。内部记录有事实引用、正文提到「你」或向用户送票，并不足以证明用户实际感到了联系。以上记录现象与用户反馈，具体原因尚待讨论，不提前归结为单一提示词或资料不足问题。

后续讨论应覆盖：如何选择实际可用且对用户有意义的上下文；领养相遇为什么与这位用户有关；宠物性格如何通过具体行动回应用户；共同经历怎样持续积累并在后续故事、成长与家中被感知；如何检查故事正文里的联系，而不是仅核对内部 basis 或 JSON 字段。

修复继续遵守事实边界，不编造用户行为、情绪或偏好，也不把每篇故事强行写成固定隐喻或重复的「你做了什么，所以宠物做了什么」。宠物可以有自己的生活，但自主生活与建立用户关系应如何共同发挥作用，需要与此前「无新用户经历时的定时表达」问题一起讨论。验收需包含用户对关系感的实际反馈，不能以模型自评或合同通过代替。

本次只记录问题，不重写已发生的故事，不改变个体、基因或性格，不修改当前插件和定时任务；具体修复方案未决定。

### 领养故事的意义与用户关联

核心目标是让用户觉得这段获得宠物的经历有意义，并感受到生成的宠物与自己有所关联。

Agent 从实际可用的资料与活动中自行寻找对用户有意义的关联，将其转化为获得蛋的经历和地点，再让地点为基因生成提供语境。资料范围与取舍由当次任务决定。宠物的探险可以是虚构的；涉及用户实际经历的内容需要有资料依据。

工程上需要让 Agent 能够获取相关上下文并保存本次使用的依据，使故事、地点与基因的关系能够延续。资料不足时如何形成有依据的内容，由 Agent 根据当时情况判断，不预设统一的领养流程。

验证方式需要包含用户对意义和关联的判断。自动检查可以帮助核对资料依据与内容是否连贯，但用户是否感到这只宠物与自己有关，需要用户的实际感受来验证；具体收集方式尚未确定。

### 基因的生成保存与形象表达

基因需要成为同一只宠物后续进化和图像生成能够持续使用的身份依据。

领养故事如何决定灵感来源、主要形态如何转化这些依据、各阶段如何发展个体特征，以及变化如何延续身份，由 Agent 根据元规则与该个体的记录形成具体设计。

工程上需要支持开放描述的保存与读取，将基因、已有形象和变化记录绑定到同一宠物编号，并在生成时提供相应参考。

基因表示使用开放的自然语言：保存熟悉的灵感来源、为什么由这段领养故事选择它、主要身体特征如何转化这些依据，以及个体识别与阶段发展。生成时形成具体内容，工程层提供必要的存储和读取格式。颜色与纹理可以参与形象，但不足以单独承担身份设计。

0.5.0 将基因作为开放文本，与宠物编号、领养地点和故事引用一起保存，具体字段见 [存储合同](../framework/references/storage.md)。不同宠物可以具有不同的形象构成，不要求填满同一份身体部件清单；随机来源的记录也不等同于重新调用生成工具便能复现相同结果。

基因单元新增开放的 `designBasis` 字段，保存简短的来源、故事选择理由与形态转化说明。它保存在既有内部步骤中，同一依据也保留在持久基因文本中，后续仅读取 genes 即可延续；不新增灵感数据库或顶层宠物数据结构。旧个体缺失的历史依据保留未知，不事后编造。

验证先在生图前检查设计依据是否成立，再查看实际图像是否体现来源与有依据的转化，以及同一只宠物跨阶段是否仍能被识别。多个设计可以相近，差异大小不能证明设计有效。用户是否觉得是为自己设计的宠物，仍由用户实际判断。

### 宠物经历与文本图像的开放生成

工程上需要支持故事内容、状态变化及表达形式的生成，而明信片、照片、OOTD、时间表等保持为示例。

Agent 结合用户当前情况与宠物自身经历，先形成当次的新故事，再以故事为依据决定状态、形象变化及文本与图像表达。该关系说明内容的决定方向，具体工具执行方式保持轻量，由 Agent 根据任务组织。

状态形象可以保存和复用。工程上提供该宠物已有素材及必要的上下文说明，Agent 自行判断是否适合本次故事，不要求每次新故事都重新生成一套状态形象。

生成机制保留内容与形式的空间，同时由 Agent 检查用户关联、宠物身份和经历是否连贯。0.5.0 保存故事计划、真实素材与完成结果，组织方式见 [执行流程](../framework/references/workflow.md)；语义和实际图像仍需要生成检查与用户验证。

内部生成结果与对话框故事输出需要明确衔接：保存新故事及其决定的状态、形象与素材结果，使用合适的已有形象或完成新素材，并按唯一编号更新目标。面向用户呈现这段故事的文本与图像，最终表达与实际完成的更新相符。调用失败、没有新增变化或素材未完成时，Agent 根据实际结果自行组织宠物内容，继续遵守故事输出边界，避免虚构已经发生的变化。

### 插件需要持久保存的数据

存储围绕宠物身份、经历与素材组织，让后续调用能够继续同一只宠物、生成连贯故事并复用已有形象。以下内容已由 0.5.0 的轻量记录实现，具体字段见 [存储合同](../framework/references/storage.md)。

| 数据内容 | 需要保存的信息 | 用途 |
| --- | --- | --- |
| 身份与目标绑定 | 宠物唯一编号、创建或领养时间、对应宿主的 Avatar 标识及必要定位信息。 | 重启后仍能找到并更新同一目标，两端各自管理自己的宠物。 |
| 基因与领养来源 | 熟悉灵感、领养故事选择理由及主要形态转化依据，个体识别与阶段发展，地点和领养故事引用。 | 延续有依据的设计与身份，保留形象和获得经历的联系。 |
| 当前阶段与状态 | 当前阶段、已采用的状态描述、当前形象和相关故事引用、最近更新时间。 | 让 Agent 知道宠物现在是什么状态，宿主应该使用哪个形象。 |
| 故事与变化记录 | 故事编号或其他稳定引用、时间、文本、图像引用、相关状态与形象，以及变化的简短依据。 | 延续宠物经历，支持进化判断；依据可包含本次采用的用户关联事实和近期变化摘要。 |
| 可复用的视觉素材 | 实际图像文件及稳定引用、用途描述、相关基因或阶段与状态说明、来源故事。保存身份参考、状态形象、故事图像及宿主所需素材。 | 让 Agent 判断素材是否适合新故事，复用或作为后续生成参考。用途保持开放，不构成固定素材类别。 |
| 调用与续接记录 | 正在进行或最近完成的调用／触发标识、关联故事和素材、完成结果及待完成事项。 | 避免同一触发重复产生故事或变化；生成或更新中断时继续已有任务。 |

当前状态、故事与素材通过宠物唯一编号关联。一份状态形象可以被多个故事引用，复用时记录所用素材的引用。已完成的状态与形象、尚待完成的变化在记录中保持可区分，避免重试时把未完成的更新当作已经生效。

用户资料由 Agent 在运行时按需选择与读取。插件保存与宠物经历或变化有关的简短事实和判断依据，不默认复制完整用户资料、全部对话或工作记录。Agent 根据任务选择读取哪些历史，并在需要时补充简短摘要。

Avatar 是否激活在更新时从宿主读取，当前激活状态无需作为持久定位依据。更新或刷新结果若需要用于续接，可以记录实际取得的结果，并区分请求已发出与显示已经确认。

元规则与提示词保存在框架的可修改文件中。实际存在的配置覆盖或调度任务引用按需保存；第一版无需为所有可能设置预建配置项。记录格式可以保留一个简单的存储格式版本，便于以后读取已有数据。

第一版可以按宠物编号组织少量记录与图像文件。结构化部分承载编号、阶段和引用，基因、状态及故事继续使用开放描述。Dots 与普通 Pet 分别在自己的运行环境中保存，不共用同一份宠物记录。持久素材需要在后续调用中仍能读取，临时生成路径在必要时转存或关联到持久位置。

### 进化特殊变化与日常状态的判断

三种变化各有依据，具体判断由 Agent 在运行时形成：

| 变化 | 已明确的依据 | Agent 自行判断的内容 |
| --- | --- | --- |
| 进化 | 用户近期是否出现有意义的变化（不限于工作）。 | 参考范围、对变化的理解、是否进入后续阶段，以及该个体如何表现进化。 |
| 特殊变化 | 成年后，根据一段时间的用户活动随机产生。 | 活动的取舍、变化内容、影响范围和持续方式，以及如何延续身份。 |
| 新故事与日常状态 | 命令、四个默认时刻或 Dots 主动行为触发新故事，由故事决定状态与形象变化。 | 新经历、状态和图文表达，以及已有状态形象是否适合复用。 |

同一时段发生的变化如何配合，以及 Dots 额外主动产生内容的时机，由 Agent 结合当前情况与已有记录判断，并遵循直接对话的功能范围。工程上需要落实定时检查、宿主触发与重复执行防护。

### 开源框架与元设计模块

参考 GenFaceUI 论文第 3.3 节与第 4.1.1 节：设计者在设计时定义生成空间、风格不变量和上下文映射；系统在运行时据此生成具体实例。论文中的提示词由预定义提示词、SVG 模板、设计规则与上下文规则四部分按阶段组装。参见 [GenFaceUI 原文](https://arxiv.org/abs/2602.11055)。

用于 GenPet 的机制方向是：开发者能够修改生成条件与具体机制，运行时使用这些条件生成某一只宠物的形象、经历和变化。基因、进化和故事机制属于本项目需要设计的内容。

模块职责划分如下：

| 模块 | 负责的内容与可修改部分 |
| --- | --- |
| 宠物元设计 | 熟悉来源与故事依据、字面蛋、生物特征、默认像素风格，以及个体识别和跨阶段连续性的规则。 |
| 用户关联与领养 | 如何理解用户资料，形成有意义的获得经历、随机探险与地点。 |
| 基因 | 由领养故事选择灵感，形成设计依据、身体转化与基因，保存并用于后续形象生成。 |
| 变化机制 | 进化、成年后的特殊变化与日常状态变化；三者可以进一步分别组织。 |
| 故事与表达 | 先形成新的宠物经历与故事，再决定状态、形象变化及文本与图像表达；合适的状态形象可以复用。 |
| 对话输出 | 将当次宠物内容以故事文本与图像呈现给用户，执行过程和内部记录不进入对话框回复。 |
| 身份与记录 | 宠物编号、状态、基因、故事与素材的对应和持久保存。 |
| 宿主接入 | 普通 Pet 的安装与更新，以及 Dots 自有 Avatar 的安装与更新，各自使用对应环境的能力。 |
| 命令与触发 | “新故事”等斜杠命令、周期检查，以及 Dots 主动工作的接入。 |

元设计规则、各机制的提示词和执行代码可以按职责分别存放。两个版本各自使用独立的宠物记录，框架中可复用的定义与提示词不要求两端共用同一宠物实例。

提示词按当前任务引用相关元设计规则、机制说明、该宠物的身份与已有记录，以及本次可用的用户上下文。生成形象时引用已有形象参考。运行模块和任务引用方式见 `framework/prompts` 与执行流程。

实际运行提示词维护于 `framework/prompts`（早期草案已冻结于 `docs/archive/design-drafts`），构建时复制到两个插件包。元规则作为共同条件，领养与基因提示词形成该宠物的设计记录，形象提示词按蛋、首次显现或后续阶段引用相关记录。运行时使用已保存的计划与实际素材。

面向用户的 [故事输出提示词](../framework/prompts/output.md) 单独组织，供各项机制引用。其他模块形成的设计描述、执行说明和核对结果作为内部结果，最终对话内容遵守故事输出边界。

[新故事任务提示词](../framework/prompts/story.md) 负责形成故事及其决定的状态和形象表达，形象任务可以引用已保存的状态素材。故事输出任务呈现已形成的故事，不再根据先行的状态操作另补一段解释。

开发者修改机制时需保持以下关系，具体运行入口见执行流程与存储合同：

- 每个模块的职责、输入输出，以及它依赖的其他模块。
- 元设计与机制提示词分别存放后，规则的作用范围、覆盖关系和冲突如何处理。
- 开发者替换某个机制或提示词后，其他模块如何继续使用其结果。
- 修改规则后，如何通过代表性输入和生成结果检查用户关联、个体差异、同一个体的形象连续性与故事连续性。
- 默认实现、可修改文件与必要宿主接入条件如何文档化，让开发者知道从哪里开始修改。

这些模块用于组织可修改的生成机制，具体故事、状态内容和表达形式仍由运行时根据情况生成。

### 结构化生成与单元测试

提示词明确各步的输入、步骤、可观察结果和检查点。结构约定模块之间如何传递结果，基因、故事内容、资料取舍与变化判断仍由 Agent 形成。

初始化流程：上下文 → 相遇与地点 → 熟悉灵感与设计依据 → 基因 → 视觉方案 → 保存计划 → 实际素材制作 → 图像检查 → 宿主更新与完成 → 故事表达。灵感、依据与基因仍由同一个 genes 单元形成。

后续流程：上下文 → 新故事 → 变化判断 → 视觉方案与复用 → 保存计划 → 素材制作与检查 → 必要的宿主更新与完成 → 故事表达。

| 独立单元 | 可检查的中间结果 |
| --- | --- |
| context | 采用的事实、来源引用、未知内容。 |
| encounter | 获得故事、地点、用户联系及事实引用。 |
| genes | designBasis 中的来源、故事联系与形态转化，自包含的开放基因文本，以及蛋的表达依据。 |
| story | 新经历、用户联系、状态意图与图文分工。 |
| evolution | 阶段、状态、特殊变化及简短判断依据。 |
| appearance | 复用或新形象决定、实际生成请求与自己的参考文件。 |
| image-review | 实际文件的可见观察、接受或修正决定及具体修正。 |
| output | 根据真实完成结果形成的故事文本和实际素材引用。 |

中间结果保存在当前任务及完成故事的内部 steps 中，带有单元名、输入引用、结果、时间与独立编号。重复保存相同结果不会产生第二条记录，修订保留先前结果；保存步骤本身不改变宠物阶段、基因或 Avatar。对话仍只呈现故事文本与图像。

单元测试固定上游输入，只运行所选单元。例如固定相遇与地点比较多份基因，或固定基因检查视觉请求是否延续个体，或给图像检查单元一张有已知偏差的实际图片。输入、精确提示词、输出和评价依据分别保留，能够定位偏差在哪一步发生。初始化编排不被当作一次不可拆分的生成。

轻量 CLI 提供 `unit-request` 组装固定输入的请求、`verify-unit` 核对输出合同、`record-step` 保存内部结果。合同通过只说明字段与基本类型有效，用户联系、形象多样性和图像正确性仍需要语义检查、实际查看或用户判断。运行合同见 [单元说明](../framework/references/generation-units.md)，可修改定义见 [units.json](../framework/prompts/units.json)。

### 两个宿主的实现接入与主动行为

两个版本围绕共同的产品构思，在各自环境中管理独立宠物，分别确认上下文、形象更新、内容表达、持久保存与触发机制的接入方式。

官方文档说明 Dots 能在对话之间继续工作，并自行暂停和唤醒；普通 Pet 的文档描述的是动画陪伴与工作活动展示。需要分别核对二者实际开放的生成和插件接入接口。参见 [Dots 的任务机制](https://learn.chatgpt.com/codex/dots/tasks-and-memory) 与 [Pet 功能说明](https://learn.chatgpt.com/codex/pets)。

| 接入部分 | 工程上需要确认的问题 |
| --- | --- |
| 用户上下文 | 两个宿主各能提供哪些用户资料、活动和记忆，如何用于有意义的领养和后续故事？ |
| Dots 主动工作 | 已有主动能力如何触发宠物内容，插件如何提供宠物机制所需的上下文与操作？ |
| 普通 Pet 的执行 | 由哪些命令、定时任务或代理执行宠物机制，如何更新实际 Pet 条目？ |
| 独立记录 | 两端各自持久保存宠物编号、基因、状态、故事与素材，并保存唯一编号与目标 Avatar 的对应关系。 |
| 普通 Pet 形象 | 如何按唯一编号更新对应原生条目，并在目标激活使用时通过该宿主的刷新机制即时呈现？ |
| Dots Avatar | 如何按唯一编号更新对应 Avatar，并在目标激活使用时通过 Dots 自有机制即时呈现？ |
| Dots 环境安装 | 哪些工程步骤可以交给 Dots Agent 自行实现，插件需要提供哪些说明、文件与验证目标？ |
| 内容表达 | 文本、生成图片及其他故事表达分别由哪些宿主界面承载？ |
| 调度衔接 | Dots 的主动工作与四个默认时刻如何配合，如何防止同一变化被重复执行？ |
| 命令 | 斜杠命令如何接入两个宿主，如何识别用户明确发起的操作与对话请求？ |

Dots 官方说明其主体在云端运行，并拥有自己的电脑与浏览器；访问用户个人电脑属于单独的连接能力。参见 [Dots 执行环境](https://learn.chatgpt.com/codex/dots)。本项目按两个版本独立管理宠物的方向设计，因此 Dots 端需要在自身环境中落实持久记录与 Avatar 接入。具体目录、生命周期和更新接口仍需验证。

按当前设定，普通 Pet 使用现有的 Codex 原生安装与内部通讯路径；Dots 使用自己的 Avatar 自定义路径。两条路径分别实现与验证，共同遵循按唯一编号更新目标、目标激活时即时刷新的规则。

### 宠物编号与操作目标

#### 当前开发中遇到的问题

开发过程中容易出现多个 GenPet，导致无法明确区分宠物，也难以确定插件正在操作哪一只。工程上需要建立明确的宠物身份和定位机制。

#### 本地编号与操作目标

当前提出的要求是：

- 每一只宠物有一个明确、独立的唯一编号，并将编号持久保存在本地。
- 插件根据持久保存的唯一编号找到目标 Pet／Avatar，再对它执行后续操作。
- 目标 Avatar 正在激活使用时，更新完成后即时刷新显示。
- 解决开发过程中多个 GenPet 带来的身份与操作目标混乱。
- Dots 与普通 Pet 各自保存和定位自己的宠物；这里的本地记录对应各自运行环境中的持久保存位置。

落实这些要求，需要解决以下工程问题：

| 工程问题 | 需要明确的内容 |
| --- | --- |
| 身份持续性 | 同一只宠物从蛋到各进化阶段，以及特殊变化、换装和图像更新时，如何始终沿用同一编号？ |
| 本地持久保存 | 编号如何与该宠物的基因、成长状态、故事和图像记录对应，重启插件后如何继续找到它？ |
| 宿主条目对应 | 普通 Pet 的编号如何对应其原生条目，Dots 宠物的编号如何对应其自有 Avatar？ |
| 目标 Pet 的定位 | 按设定的唯一编号及其持久绑定定位目标 Avatar，激活状态用于判断是否即时刷新。 |
| 激活状态与刷新 | 各宿主如何读取目标 Avatar 的激活状态，并在更新完成后即时刷新实际显示？ |
| 重复执行 | 初始化或更新流程重复执行时，如何识别已有宠物并继续操作同一只，避免产生重复条目？ |
| 已有重复条目 | 已经存在多个 GenPet 时，如何识别它们各自的身份，并确定后续操作目标？ |
| 开发与测试 | 开发、演示或测试用的宠物与实际使用的宠物如何区分，避免混淆？ |

定位与刷新规则已确定。编号格式、本地存储结构、宿主条目的绑定方式，以及激活状态读取和刷新接口仍需在工程上实现与验证。

#### 按唯一编号更新与即时刷新

每次更新以设定的宠物唯一编号确定目标，通过持久保存的对应关系定位该编号的 Pet／Avatar。若宿主使用独立的 Avatar 标识，工程上保存其与宠物编号的一一对应关系；两个版本分别管理自己的绑定。

在同一目标条目上更新该宠物的形象与素材，继续沿用原有唯一编号。随后根据目标的激活状态处理显示：

- 目标正在激活使用：更新完成后即时刷新其可见形象，用户无需重新选择或重启宿主。
- 目标未激活使用：更新对应条目与记录，保持当前选择；后续使用该目标时呈现更新后的形象。

工程验证需要覆盖目标激活与未激活两种情况，并核对实际更新的条目和可见形象。刷新请求被接收与实际显示新形象需要分别验证，内部执行记录继续遵守对话框的故事输出边界。

#### 当前实现

代码结构、模块职责与扩展方式见 [代码架构](ARCHITECTURE.md)。要点：

- 记录按 desktop／dots 分开保存，每只宠物有独立 ID；读取状态不改变成长阶段或用户资料。
- 一次触发只对应一个未完成故事，重复调用延续同一任务，完成时才一并提交阶段、状态与历史。
- 宿主差异集中在 `src/hosts/`：普通 Pet 写入该 ID 的唯一原生条目并经 IPC 请求刷新；Dots 由其 Agent 用自有工具更新已绑定的 Avatar，再回报结果。
- 旧 v1 记录只在明确迁移时导入，保留 ID、阶段、形象与绑定；明确重置时新身份接续已有宿主条目。

接入代码或刷新请求成功本身不能替代视觉证据。旧的重复条目不会被自动删除，只按已明确的持久绑定操作目标。

## 后续需要落实的工程与验证

资料选择、参考范围、进化触发与具体内容交给 Agent 运行时判断。后续工作集中在让这些判断能够可靠执行，以及检验实际生成效果：

| 工作部分 | 需要落实或验证的内容 |
| --- | --- |
| 上下文接入 | 各宿主实际能提供的资料、活动和记忆，如何由 Agent 选择并用于当次任务。 |
| 身份与操作目标 | 按唯一编号绑定和更新目标 Avatar，以及重复调用时延续同一只宠物。 |
| 持久记录 | 按数据内容草案落实身份与绑定、基因、当前状态、故事、可复用素材及续接记录的保存和读取。 |
| 模块与提示词 | 各机制引用相关元规则、宠物记录与上下文的方式，以及开发者替换模块后的组合方式。 |
| 宿主接入 | 普通 Pet 与 Dots Avatar 各自的安装、更新、激活状态读取与即时刷新；Dots Agent 自行完成环境接入的可行性。 |
| 命令与调度 | 将原状态变化入口替换为新故事命令，接入四个默认时刻与 Dots 主动工作，并防止重复执行。 |
| 故事输出 | 内部结果与用户可见故事的衔接，确保各项机制只在对话框呈现故事文本与图像。 |
| 生成效果 | 生图前检查熟悉来源与故事决定的设计依据；实图检查其可见表达、字面蛋、生物特征、无脸生物及身份与故事连续性。 |
| 旧实现替换 | 移除旧固定家族、形态枚举、统一造型提示词与固定天数进化的生成基础，接入新的 Agent 判断与开放生成机制。 |

## 0.5.0 开发交付与验证边界

两个安装包为 `plugins/genpet-dots`（主要版本）和 `plugins/genpet`（普通 Pet）。`framework/prompts`、`framework/references` 为共享可修改来源，构建时复制到各包；安装后的 Agent 读取本包文件。运行时保存六类数据，并将生成决策留给 Agent。

本轮执行代码单元检查与 subagent 的静态形象／故事生成单元验证。按照用户要求，不执行动画生成或真实宿主端到端验证，也不通过本轮开发操作真实宠物或调度。2026-10-02 跨设备交付前，完整 release gate 已在隔离环境通过；这不证明实际生成效果或宿主显示。用户验证入口与当前证据见 [新版验证说明](NEW_VERSION_VALIDATION.zh-CN.md)。
