# GenPet 测试后的开发计划

2026-10-08，讨论草案。当前先讨论故事体验，确认方向后再拆成开发任务。测试问题与记录见 [工程问题记录](ENGINEERING.zh-CN.md)，长期陪伴的设计参考见 [体验调研](research/companion-experience/REPORT.zh-CN.md)。

## 已确认的目标与约束

- 通过故事建立这只宠物与这位用户的联系，让用户感受到持续陪伴、发现和期待。
- 用户应当出现在宠物故事里，依据是真实的用户与宠物交互，包括宠物实际可见的用户资料、用户的交互输入及反馈。不能通过虚构用户参与来制造联系。
- 用户资料获取需要真正做出来，从拿到蛋的第一次相遇开始服务于关系建立；不能只有「结合用户资料」的要求而没有读取过程。
- 连续检查没有新故事、没有有体验的文字反馈，已经被用户明确反馈为无聊，需要修复。
- 每次五小时检查都要有宠物内容，长短由当次经历决定。这是用户在本轮讨论中明确选择的行为。
- 用户可见文字应有体验；执行机制放在后台读取的文档中。
- 用户事实需要真实来源；宠物世界可以虚构，不能借此编造用户行为、情绪或偏好。
- 内容与判断保持开放，由 Agent 结合上下文、性格和历史决定，不增加固定题材菜单、穷举预设或不必要的配置。
- 更新同一只宠物，保留用户选择；不调用或依赖 Computer Use。

## 故事体验

### 当前问题

最近的定时检查连续跳过，只有过程预告，没有新的宠物经历。此前领养、成长和自主生活故事，也未让用户充分感到关联。增加消息数量、在正文里加上「你」，都不能单独解决这两个问题。

### 用户资料获取与领养的实现缺口

2026-10-08，用户补充：拿到蛋的故事也基本没有用户联系，当前实现没有获取用户资料。检查现有实现后确认，context 的输入是外部提供的 availableContext；运行时提供单元输入、格式检查与结果保存，workflow 只要求 Agent 自行选择上下文，没有实现生成前读取用户资料的操作步骤。现有 status 读取的是宠物记录与已保存的对话摘要，不是用户资料获取入口。

本只宠物的领养 context 实际采用本聊天里的环境清理、斜杠入口去重、领养确认和中文使用。领养依据明确记为没有其他生活资料；这些来源是真实的，但没有体现对用户有意义的了解，最后形成了围绕插件操作的驿站故事。问题同时存在于信息获取和领养内容，不能只通过修改措辞处理。来源见 [context 的输入输出格式](../framework/prompts/units.json)、[workflow](../framework/references/workflow.md)、[运行时单元处理](../src/generation.ts)和 [status](../src/status.ts)；领养事实来自当前这只宠物已保存的首篇故事 context 结果。

开发先实现轻量的实际读取流程：在初始化和每次故事的 context 之前，Agent 检查所在宿主实际可用的用户资料与交互来源，按有意义的资料读取，再将简短摘要与来源交给 context。资料选择与观察范围继续由 Agent 判断，不建设固定用户画像或穷举来源系统，也不假设宿主可读用户所有历史。

领养使用读到的真实用户资料形成相遇缘由，进而影响地点、设计依据与蛋的线索；后续故事使用新的真实输入与已有真实交互的延续。读取结果不足时需要如实保存缺口，怎样完成有意义的领养与当次表达仍需讨论，不能用纯虚构用户参与填补。

验收分别检查：是否实际读取了来源、哪些真实的用户资料进入 context、领养或故事正文怎样具体回应，以及用户是否感到联系。只有一个 availableContext 字段、事实摘要或模型自评，不能证明获取链路和关系体验已经成立。

### 已确认的原则：故事里要有真实的用户

2026-10-08，用户指出现在的故事完全没有建立联系，小乐队没有用户参与，并进一步明确：故事里的用户要来自真实的用户与宠物交互，包括宠物看到的用户资料和用户交互输入。把用户作为角色编进虚构经历，没有意义；这一方向已被否定。

当次故事先识别实际可用且有意义的用户资料，再由宠物的性格、当前状态和既有经历形成回应。故事正文应让用户看得出它留意了什么、怎样回应，以及这次真实交互如何影响彼此后续的相处。只在内部保存事实引用，或在纯自主故事结尾提到「你」、附一句邀请，都不足以证明联系成立。

真实的用户资料可来自用户明确对宠物的输入、请求与反馈，也可来自宿主实际可见的用户资料；范围不限于工作，也不要求用户每次使用斜杠命令或额外完成操作。用户说过、做过什么需要来源；不凭空写用户听了演奏、参与探险或作出回应。

宠物世界与宠物回应可以采用幻想表达，但建立关系的用户资料和交互必须真实。宠物的性格与独立生活继续保留，不能靠完全独立的虚构剧情替代用户联系。没有新资料时，可以回到尚有意义的真实输入及其后续影响，怎样避免机械重复仍待讨论。

### 已确认的检查表达

2026-10-08，用户选择「每次都有宠物内容，长短由当次经历决定」。正常完成的每次五小时检查都应呈现当次宠物内容，不再因缺少新的用户事实且成长未到期而直接取消并留空。

长度由具体经历决定，不规定每次都写完整长故事。每次有内容不意味着每次都要改变状态、成长、换形象或配图；这些继续由故事和实际完成结果决定。内容仍须来自宠物世界，不能用检查报告或过程预告代替，也不能编造用户事实。

开发时需要一起调整 meta 的故事节奏、workflow 与 scheduling 的跳过分支，以及 output 的空白输出规则，避免不同文件仍要求相反行为。无新用户资料时内容如何发展、怎样建立用户联系，继续在下面讨论。

### 待讨论决定

1. 先核实宿主实际可用的用户资料与交互来源，明确生成前的读取步骤，再讨论哪些有意义的资料应进入领养与后续故事。
2. 没有新用户资料时，怎样延续已有真实交互的影响，每次仍有内容，避免虚构用户参与、重复问候或填充文字。
3. 什么内容足以成为一次值得分享的经历，短小进展怎样表达，避免每次都重复同一种结构。
4. 从第一次领养起，真实用户资料如何引起宠物的回应，用户后续反馈又如何影响下一次回应并积累为共同记忆。
5. 连续故事怎样留下记忆与期待，同时避免固定剧情、重复套路和持续催促用户。
6. 图片在体验中的作用，以及哪些内容只用文字就足够。

### 确认方向后的开发范围

开发顺序先实现实际用户资料读取，再调整 context、encounter、initialization、story、chat、meta 和 output：context 选择有来源的用户资料，encounter 从第一次领养建立具体联系，story 形成宠物回应，后续上下文保留值得延续的真实输入与反馈。用户事实和生成的宠物世界内容分别处理，不能把生成的互动当作真实用户资料。使用现有记录与单元结果保存能力，只有现有记录无法支持已确认行为时才增加工程字段。

先用领养、没有新用户资料、只有旧的用户资料和连续数次检查的文字样本比较体验，并以小乐队故事作前后对照。每个样本核对真实用户资料的来源、正文的具体回应，以及用户反馈如何进入后续内容；不为修复旧故事补造用户对音乐的兴趣或已经参加演奏。继续核对性格与历史连续性，由用户判断联系是否成立、是否愿意继续看。样本得到认可后，再修改运行规则和安排完整宿主测试。

## Context 模块细化草案

本节细化生产流程中真实用户资料的获取、理解与传给下游，具体方案待讨论确认。context 的目标是让下游知道用户实际表达了什么、有哪些有意义的近况，以及这只宠物此前怎样回应过。故事情节与宠物反应由后续单元创作。

### 获取与处理流程

| 环节 | Agent 需要完成的工作 | 可核对结果 |
| --- | --- | --- |
| 理解本次任务 | 结合当前输入、初始化或后续调用、宠物记录与时间，判断这次需要了解什么 | 本次资料选择的简短依据；诊断请求不误当故事请求 |
| 确认可用来源 | 检查宿主实际暴露的资料与读取能力，从当前上下文和已有真实交互出发，需要时再寻找相关来源 | 可用来源与访问限制，不假定能读取全部历史 |
| 实际读取 | 对需要补充的资料执行读取，保留来源定位；当前消息已经在上下文中时直接引用 | 实际读取结果或已提供的消息引用；来源列表本身不算读过内容 |
| 理解与选择 | 选出与用户及本只宠物有意义的事实、请求和反馈，核对时间、范围、纠正与已有回应 | 有来源的 facts，以及仍未知的 unknowns |
| 交给下游 | 将所选资料连同相关宠物历史交给 encounter 或 story，保存简短内部结果 | 下游能够定位真实依据，辨认已有回应与可继续发展的联系 |

来源选择与观察范围由 Agent 按本次需要判断，不规定固定天数、固定查询轮数或固定资料分类。当前请求和用户对宠物的直接反馈应首先被理解；它们不够时，再根据可用能力补充与用户有关的资料。内容不限于工作，也不把一次插件测试操作机械转成生活主题。

### 输入和输出

生产 context 需要当前用户输入或定时任务目的、实际可用的来源能力、已有真实交互，以及相关 pet、近期故事和 time。宠物已有回应提供相处背景，不能当作用户真实做过的事。来源能力用于决定怎样读取，实际资料才进入 availableContext。

第一轮尽量复用现有结果结构：inputRefs 记录实际读取结果或已提供资料的定位；facts 保留 id、text、source；unknowns 保留影响本次理解的缺口。事实确有时间信息时，可附带简短时间说明，不从读取时间推断事件发生时间。是否需要新增字段，以实际样本不能表达的具体问题为依据。

事实摘要要保留用户表达的性质与范围：愿望不写成已经完成，提问不写成偏好，一次输入不写成长期习惯，纠正不继续沿用旧判断。未知原因、情绪和偏好留作未知。获取失败与未读取不能写成没有用户新活动。

生产流程由 skill 和 workflow 指导 Agent 执行实际读取；context 单元使用读取后的资料理解与选择。现有 unit-request 是固定输入的隔离测试入口，继续只使用测试提供的资料，不在单元测试中读取真实用户资料。不能把测试入口当成生产获取流程。

### 初始化与后续调用

初始化先了解实际用户资料及领养意愿，再交给 encounter 建立相遇缘由。安装、清理与确认可作为事实，但不能自动代表用户生活或兴趣；不足时如实记录，继续处理办法另行讨论。

后续调用关注本次真实输入、新获取的相关资料，以及此前互动的延续。传给下游时同时提供相关旧回应，帮助 story 避免机械重述同一句话。没有新资料时仍可以延续已有真实联系，但不能编造用户参与来满足每次有内容的要求。

### 第一阶段开发任务

第一阶段要交付能实际运行的信息获取与使用流程。完成标准是 Agent 从真实来源取得资料，形成可追溯的 context，领养或故事正文实际回应这些资料；仅修改提示词描述或通过 JSON 检查不算完成。

| 顺序 | 任务与修改位置 | 交付结果与验收 |
| --- | --- | --- |
| 1 | 核实桌面宿主实际可用的读取能力；记录到本仓库的开发记录 | 实际读取当前输入、相关历史或已保存真实交互的样本，记录来源定位与限制。区分已提供的资料、工具读取成功、没有权限、不可用和尚未读取。可用能力必须实测，不根据工具名称推断 |
| 2 | 在 framework/references/workflow.md 接入获取步骤；在需要时增加简短的 context 读取参考文档 | 初始化和后续故事都经过任务理解、按需读取、context 选择，再交给下游。当前已提供的输入无需重复调用工具；需要补查时必须实际读取。来源不足时留下具体缺口，不能直接解释为用户没有活动 |
| 3 | 修改 framework/prompts/context.md；按具体需要同步 framework/prompts/units.json 与 generation-units.md | context 明确保留真实输入、请求、反馈的原意与范围，并参考相关旧回应。优先复用 facts、unknowns 和 inputRefs，不增加用户画像、固定分类或读取配置菜单 |
| 4 | 调整 initialization.md、encounter.md、story.md 与相关 meta 规则 | 领养从真实的用户资料形成相遇缘由；后续故事具体回应真实输入或其延续。事实 ID 的引用同时能在正文找到对应回应，不能仅在内部 connection 字段说明关联 |
| 5 | 检查 chat.md、workflow 与现有 note-chat、record-step、status 之间的衔接 | 自然语言中的有价值输入与纠正能被后续 context 使用；只保存相关摘要。宠物对白不变成用户事实。需要查阅较旧关联时读取完整记录，而非把默认近期列表之外当作没有发生 |
| 6 | 补单元样本、实际读取记录和下游内容验证 | 工程测试检验输入与记录的可靠性，语义样本检验摘要原意和真实关联，再由用户评价故事。第一轮不生成完整动画来验证 context |

任务 1 的实测结果决定任务 2 的具体工具路径。生产读取由 Agent 使用实际可用能力执行，不先建设新的数据服务。只有实测暴露出已有工程能力无法支持的具体问题，才修改 src/generation.ts、src/chat.ts、src/status.ts 或其他运行时；不为了表示有功能而新增空的读取接口。

定时检查每次都要有宠物内容的规则，需要同步调整 workflow、scheduling 与 output，但不能用虚构用户资料来满足。自然语言加载与诊断请求走下面的诊断流程，不写成宠物故事或用户参与事实。

### 验收样本

| 场景 | 必须核对的行为 |
| --- | --- |
| 初始化取得真实用户资料 | 有实际来源读取或已提供资料；相遇与设计依据能具体回应这些资料，不只映射安装操作 |
| 用户对宠物发出明确输入 | context 保留输入原意，故事表现宠物回应；不将愿望写成已发生的用户行为 |
| 用户纠正先前理解 | 使用纠正后的事实，后续不继续沿用被否定的判断 |
| 相关历史在当前上下文之外 | 实际读取需要的历史内容，保留定位；只看到标题或摘要不足时继续核对原始内容 |
| 同一条资料跨周期延续 | 对照此前宠物回应，发展其后续影响，避免只重复用户原话或同一承诺 |
| 读取失败或没有新资料 | 分别记录读取限制与事实缺口，不编造活动、情绪或用户参与；当次表达仍遵守已确认的规则 |
| 存在不相关或过时资料 | 按本次目的取舍，核对事件时间和用户纠正，不将旧信息误当最新近况 |

隔离单元样本可放在现有 tests/agent/contexts 中；涉及字段格式和记录的实际改动时，在 tests/generation.test.ts、chat.test.ts、status.test.ts 等对应位置验证。真实宿主读取记录保存在仓库的开发记录目录，只留相关摘要和来源定位，不保存整份私人历史。

### 交付与发布

第一阶段完成后，先让用户查看领养与连续故事的文字样本，确认真实联系成立，再完成发布检查和安装验证。发布版本按项目规则递增并重建插件；读取与领养测试使用独立测试记录，不重新领养或重置用户当前这只宠物。当前文档是在细化开发范围，以上任务尚未实施。

## 加载、缺失与显示异常的诊断和修复

2026-10-08，用户提出「加载我的 genpet」，实际需求是：宠物没有显示在桌面上，并且在 Codex 的 Pet 设置里也找不到。Agent 当时只读取宠物记录、展示已有图片，并用「我在这儿」等宠物对白回应，没有执行客户端加载或确认故障；用户明确要求技能支持此类诊断和修复。本次先记录需求，尚未实现。

已确认的方向：

- Agent 结合用户输入和上下文识别实际意图。「加载」「找不到」「不显示」等请求应先确认 GenPet 与宿主情况，再执行对应操作，不能直接归入宠物聊天，也不要求用户记住专用斜杠命令。
- 以现有宠物 ID 和绑定定位宠物，检查本地记录、宿主 Pet 列表、本地到云端迁移映射、实际选中状态，以及接口可提供的窗口与宠物显示状态。按查到的实际情况判断故障；不能仅凭本地文件存在或选中 ID 推断已显示。
- 在用户请求授权的范围内修复实际故障，例如重新选择正确目标、刷新对应资源；维护同一只宠物，不因界面缺失而重新领养、重置、推进成长或生成形象。使用宿主 API、app-tools、IPC 和插件运行时，不依赖 Computer Use。
- 诊断和修复使用简短、直接的操作说明，明确确认了什么、执行了什么、还有什么未知。调整技能、workflow 和 output 的适用边界，使宠物世界对白用于陪伴与故事，不能覆盖用户要求的故障诊断或冒充加载成功。
- 修复后核验对应宿主结果，分别表达列表存在、选中状态、刷新请求送达和实际显示情况。接口无法确认或控制显示时，如实说明具体限制，只给用户必要的一步操作。
