## 已确认的目标与约束

**它和用户的关系**

- 通过故事建立这只宠物与这位用户的联系，让用户感受到持续陪伴、发现和期待。
- 用户应当出现在宠物故事里，依据是真实的用户与宠物交互，包括宠物实际可见的用户资料、用户的交互输入及反馈。不能通过虚构用户参与来制造联系。
- 用户事实需要真实来源；宠物世界可以虚构，不能借此编造用户行为、情绪或偏好。
- 用户资料获取需要真正做出来，从拿到蛋的第一次相遇开始服务于关系建立；不能只有「结合用户资料」的要求而没有读取过程。
- 宠物的基因对应用户的特质（性格、情感倾向等，用户称为用户的「基因」）。用户的活动用作故事和对话的上下文，基因设计依据用户特质。
- 领养是一段由用户做选择的旅程故事：用户资料决定故事背景，用户一路选择，直到得到蛋。

**每次的内容**

- 连续检查没有新故事、没有有体验的文字反馈，已经被用户明确反馈为无聊，需要修复。
- 每次五小时检查都要有宠物内容，长短由当次经历决定。这是用户在本轮讨论中明确选择的行为。
- 用户可见文字应有体验；执行机制放在后台读取的文档中。
- 故事和宠物设计都要有随机性。用户资料没有变化时，每次故事的设计也不一样。
- 定时检查在用户的电脑上运行。电脑关机或 Codex 没有运行时不会触发，所以实际一天可能只有一到三次检查，不能按一天四五次来设计节奏。
- 弱交互：不强调用户和宠物的直接互动。宠物的内容不向用户提问，不邀请、不暗示用户要回应。例外只有一处：孵化的时候请用户给它起名。

**宠物设计**

- 宠物设计要多样。自然生物可以保留，同时从不同文化的传说和作品里取想法，例如发光的小精灵、外星小狗。
- 可爱是前提。不出现让人不适、不喜欢的形象。来自普通动物或植物的宠物，也要有趣、可爱。
- 孵化后的宠物不要求像动物，但要有五官特征，至少有眼睛。
- 宠物设计要具体。灵感来源写到具体的品种、具体的传说或具体作品里的具体形象，再设计它的属性、能力和特殊的器官或结构。「猫加翅膀」「绿壳蜗牛」这种写法不算设计。

**安全和开发原则**

- 安全优先：健康、财务、人际矛盾等敏感资料，以及可能涉及隐私的内容，不写进故事，也不保存进宠物记录。拿不准时按敏感处理。
- 开发原则：能交给 Agent 决定的都交给 Agent。只有必须保证稳定的关键功能，才用代码和固定规则。
- 不做过度设计，不做过度工程。这既是设计原则，也是写代码的规则：Agent 能处理的情况，不写代码、固定规则或额外流程去限定它。例如用户不同意领养前的说明，Agent 停下来说明即可。
- 内容与判断保持开放，由 Agent 结合上下文、性格和历史决定，不增加固定题材菜单、穷举预设或不必要的配置。
- 更新同一只宠物，保留用户选择；不调用或依赖 Computer Use。

## 整体安排

2026-10-11 确认目标、设计原则和开发顺序。

这个项目还没有公开发布过。所有开发完成、功能都实现之后，发布一个公开上线的版本。中间各段不单独发布。

目标：按一个顺序开发，每一段结束时用户能看到样本并判断，再进下一段。

设计原则：

1. 先实测宿主能做什么，再开发依赖它的功能。
2. 基础先做，记录版本只升一次。
3. 每一段结束有用户能直接看的样本，由用户判断是否通过。
4. 全程用测试记录和隔离的 `CODEX_HOME`，用户正在养的那只保持原样。

| 段 | 做什么 | 结束时用户能看到 |
| --- | --- | --- |

## 读用户资料

2026-10-08 到 2026-10-10 确认。起因：测试里拿到蛋的故事和之后的故事都没有用户联系，检查后确认当时的实现没有读取用户资料的步骤。

目标：领养和每次故事之前，Agent 真的读到了这位用户的资料，内容因此和这位用户有关。

设计原则：

1. 真的去读。只写「结合用户资料」的要求而没有读取步骤，不算完成。
2. 优先使用 Codex 已经整理好的用户记忆，GenPet 不另外保存一份。
3. 读什么、读多少，由 Agent 按这次的需要决定。不建用户画像，不规定固定天数和来源清单，代码里不写死路径。
4. 用户的事要有来源，并保留原意：愿望不写成已经完成，提问不写成偏好，一次输入不写成长期习惯，用户纠正过的不再沿用。
5. 读取失败和没有新变化是两件事，分开记录。
6. 敏感和隐私内容不使用，也不保存。
7. 单元测试只用测试提供的资料，不读真实的用户资料。

用户资料有两种用途：用户特质（性格、情感倾向等）用来设计宠物基因；用户活动用作故事和对话的上下文。

孵化之后（2026-10-10 确认）：对用户特质的了解在之后每次 context 里继续更新，新的了解会影响宠物之后的成长。

对用户的了解保存在哪里（2026-10-10 确认）：

- 优先直接使用 Codex 已经总结好的用户记忆。能读到时，GenPet 不另外保存一份「对用户的了解」。每次 context 读 Codex 记忆，加上宠物记录里已有的旅程记录和对话记录，由 Agent 当次形成了解。
- 领养和每次成长用到了哪些了解，写在已有的设计依据和成长依据里，之后能查到当时的理由。
- 读不到 Codex 记忆时（功能没开、Dots 端），参考 Codex 的做法自己实现：原始记录加一份由 Agent 定期重写的简短总结。

本机初步查看（2026-10-10，只看了文件名、大小、日期和标题，没有读正文）：`~/.codex/memories/` 存在，`config.toml` 里 `memories = true`。目录里有 `memory_summary.md`（418 行，含 User Profile、User preferences、General Tips、按项目和日期整理的 What's in Memory）、`MEMORY.md`（3321 行）、`raw_memories.md`（6493 行）和 `rollout_summaries/`（117 个文件），当天 15:42 还在更新。Codex 的做法是分层的：每次会话的原始记录 → 每次会话的总结 → 合并后的记忆 → 一份简短总结。

第 0 段要在 Codex 里实测的内容：

1. GenPet 的会话和定时检查里，Agent 能否读到这些文件，或者这份总结是否已经自动出现在 Agent 的上下文里。
2. 记忆里关于用户本人的内容有多少。标题显示它以项目和工作为主，性格和情感方面可能很少，这部分靠旅程里的选择补上。
3. 用户和宠物的对话会不会被 Codex 自己总结进记忆。
4. 文件位置和格式由 Codex 决定，升级后可能变化。由 Agent 在运行时确认可用的来源，代码里不写死路径。

对应的测试用例：A4、A5、A6（领养），T1、T3、S3、S12（故事）。

## 领养

目标：用户通过一段自己做选择的奇遇得到一颗蛋。这只宠物的身体、性格，以及它和用户的关系，都对得上这位用户。

顺序：说明和确认 → 读用户资料 → 相遇旅程（最多 5 轮）→ 基因和性格 → 蛋的形象 → 总结。

对应的测试用例：[A1 到 A10](TEST_CASES.zh-CN.md#领养)，形象用例 V1。五个手写的旅程和结果见 [领养旅程案例](ADOPTION_CASES.zh-CN.md)。

### 领养前的说明和确认

2026-10-11 确认：宠物会读用户资料这件事要告诉用户。初始化的时候给用户看一段简短的说明，像一份很轻的用户协议，用户确认后再开始。

说明里要讲清的内容：

- 宠物会读什么：Codex 已经为用户整理的记忆，和这台电脑上与宠物有关的记录。
- 读来做什么：设计这只宠物，写它的故事。
- 敏感和隐私内容不使用，也不保存。
- 宿主是 Codex，用户数据由 Codex 负责处理。GenPet 只是一个插件，自己不收集用户数据。

设计原则：

- 轻量。只在第一次领养前出现一次，几句话，一次确认。
- 用直接的话写，不用宠物的口吻。
- 说明里的每一句都要和实际情况一致。发布前开发的人要核对实际的数据去向，再定稿。

示例文字见 [领养旅程案例](ADOPTION_CASES.zh-CN.md#领养开始前的说明)。

用户不同意时：直接停止，并向用户说明没有开始领养。这由 Agent 处理，不为它写代码或另一套流程。

### 领养旅程和基因设计

2026-10-10，用户确定的思路：

- 用户资料有两种用途。用户特质（性格、情感倾向等）用来设计宠物基因；用户活动用作宠物故事和对话的上下文。
- 初始化时，Agent 结合用户资料决定故事背景，生成一段旅程故事。用户在旅程里做选择，一路走到得到蛋。
- 用户在旅程里的选择是真实的用户输入，和读到的用户资料一起成为基因设计的依据。资料很少时，旅程里的选择仍然提供真实依据。
- 开发时实测能否直接读取 Codex 已经建立的用户记忆。

领养流程和基因模块的输入输出（2026-10-10 确认）。基因模块对应架构里的 GeneDesigner，包含相遇、基因、性格三个单元：

| 步骤 | 做什么 | 结果 |
| --- | --- | --- |
| 1. 读用户资料 | 读 Codex 记忆和其他可用的用户资料，了解用户特质 | 用户特质，每条带来源；旅程的故事背景 |
| 2. 相遇：领养旅程 | 多轮进行。每轮给出场景，用户做选择；最后一步得到蛋 | 一份旅程记录：故事背景、地点、每一步的场景和用户的选择、得到蛋的经过 |
| 3. 基因和性格 | 根据用户特质和旅程记录设计这只宠物 | 设计依据、基因文本、宠物的性格 |
| 4. 蛋的形象 | 根据基因生成蛋的图 | 蛋壳样子和实际图片 |
| 5. 总结 | 把这次领养讲给用户 | 用户看到的领养总结 |

- 旅程记录是一份结果，同时包含选择和故事，一起交给基因和性格。
- 用户特质同时决定宠物的身体和性格。
- 宠物和用户是什么关系由 Agent 设计，可以相似，也可以互补。规则参考人和人的关系：两个人怎样相处出火花，形成互相陪伴的关系。开发时先做调研，把结论写进产品规则，Agent 按规则为每位用户设计，设计依据里写明这只宠物和用户的关系。
- 领养时用户另外提出的形象要求，基因模块不单独支持。

随之要改的现有内容：

- `genes.md` 的输入去掉「用户明确的形象要求」。
- `generation-units.md` 把「推断用户性格」列为性格单元的错误。改成：对用户特质的理解要有来源（哪条记忆、哪次选择），没有来源的猜测才算错误。
- 架构文档里 `context` 归在 StoryDesigner 下面。读取用户资料这一步由 GeneDesigner 和 StoryDesigner 共用（2026-10-11 已在架构文档里写明）。

旅程的形态（2026-10-10 确认）：

- 领养旅程是一次奇遇，蛋是在奇遇里意外得到的。故事不讲成去找一颗蛋。
- 旅程里可以遇到各种角色。宠物自己第一次出现时，是一颗字面意义上的蛋。
- 相遇故事最多 5 轮，在这个上限内由 Agent 按故事决定几轮。
- 故事要让用户觉得有趣、被吸引、对后面有期待。
- 每位用户的旅程都不一样：背景、场景和选项都由 Agent 结合这位用户的资料当场生成。

按开发原则，旅程分成固定的部分和交给 Agent 的部分。

固定的部分，用流程和代码保证：

- 用户做一次选择算一轮，最多 5 轮。
- 每一轮的场景、选项和用户的原话或选择都保存下来。用户中途离开后，可以从保存的地方接着走。
- 故事里用户做了什么，只来自用户自己的选择。
- 对用户特质的理解，每条带来源：哪条记忆，或哪一轮的选择。
- 敏感资料和可能涉及隐私的内容不使用，见「已确认的目标与约束」的安全优先。
- 顺序：旅程结束 → 基因和性格 → 蛋的图 → 总结。更新的是同一只宠物。
- 领养总结只讲旅程、蛋和蛋壳线索的来由，孵化后的样子留到孵化时。

交给 Agent 的部分，提示词只写目标和判断参考：

- 开场：用哪些用户资料、转成什么地点和处境、留什么悬念。参考是用这位用户自己的具体细节，用眼前的怪事让用户想往下走。读到的资料很少时，Agent 从领养当下出发，靠旅程里的选择了解用户。
- 选项：给几个、写什么。参考是每个选项是一个看得见的去处或东西，各露出一点不同的线索，用户因为想知道才选；选一个就放下另一个，好处和代价都摆出来；没有标准答案。从用户被什么吸引、愿意为什么付出代价来了解用户。用户可以用自己的话回答。
- 下一步：这次选择带来什么后果、前面的选择怎样在后面起作用、给蛋留下什么线索、什么时候结束。参考是后果兑现选项里的线索，再多给一点没想到的。
- 对用户的了解：怎样从选择和记忆里理解用户特质。参考是一次选择只说明当时的倾向，选择和记忆不一致时两条都保留。
- 读哪些来源、在安全优先的范围内用哪些资料。
- 旅程中是否配图。参考是用户在等结果，画图要花时间。
- 宠物和用户是什么关系。

开发时调研两类做法，把结论写进提示词的参考：人和人怎样形成互相陪伴的关系；用开场选择决定角色的游戏（如《宝可梦不可思议迷宫》的开场问答、《创世纪 4》的两难选择）。

五个手写的旅程和结果示例见 [领养旅程案例](ADOPTION_CASES.zh-CN.md)，用来讨论方向。

### 随机性、多样的宠物设计、可爱是前提

2026-10-10，用户指出两个问题：用户资料不变时故事容易雷同；之前生成的宠物大多直接来自自然生物。确认的方向见「已确认的目标与约束」里对应的三条。

没有新用户资料时故事从哪里来，由 Agent 选。提示词列出可以用的来源作参考：领养旅程留下的线头（没选的去处、遇到的角色、没做完的事）；以前真实互动的后续；宠物按自己的性格过日子，没什么大事就写短的；隔了很久没见时写时间本身。一条线头用过后往前推进或了结。

随机的实现（2026-10-10 确认）：做一个工具生成随机数作为种子。Agent 先列出几个差别明显、都有依据的候选，用种子选出一个；候选作为中间结果保存。故事和基因设计都用这个办法。

宠物来源的类型和出现机会（2026-10-10 确认）：不同类型的来源出现的机会不一样，大部分宠物来自大家熟悉的自然形象，少数来自更特殊的来源。「抽卡」「稀有度」只是比喻，这是背后的机制，用户看不到，也不做抽卡玩法。

| 出现机会 | 来源类型 | 起始概率 |
| --- | --- | --- |
| 大部分 | 自然界的动物和植物 | 70% |
| 少数 | 日常物件变成的生命（变形、拟人） | 20% |
| 很少 | 传说、神话、作品里的形象，以及其他幻想出来的生命 | 10% |

- 工具给出来源类型和种子，Agent 在这一类里列候选，用种子选一个。
- 类型只决定来源。每一类的设计都要同样具体、有趣、可爱。
- 概率写在代码里一个地方，看过样本后再调。

规则改动：`AGENTS.md` 的三条设计规则已按确认内容更新（具体的灵感来源、至少有眼睛、可爱优先）。`meta.md` 的「有依据的设计」「孵化后的生命」「故事节奏」和 `image-review` 的检查项属于插件内容，留到开发阶段改。

## 领养之后的故事

目标：用户觉得这是自己在养的一只宠物。每次检查都能感受到它，内容和自己有关，每次不一样，并且对后面有期待。

用户看到内容的地方有两处：桌面上的宠物，和定时任务所在的那个对话里的一条消息。平常的检查多数是换装。

对应的测试用例：[T1 到 T13、S1 到 S23、V4](TEST_CASES.zh-CN.md)。六个手写案例见 [领养之后的内容案例](DAILY_CASES.zh-CN.md)。

### 故事里要有真实的用户

2026-10-08，用户指出现在的故事完全没有建立联系，小乐队没有用户参与，并进一步明确：故事里的用户要来自真实的用户与宠物交互，包括宠物看到的用户资料和用户交互输入。把用户作为角色编进虚构经历，没有意义；这一方向已被否定。

当次故事先识别实际可用且有意义的用户资料，再由宠物的性格、当前状态和既有经历形成回应。故事正文应让用户看得出它留意了什么、怎样回应，以及这次真实交互如何影响彼此后续的相处。只在内部保存事实引用，或在纯自主故事结尾提到「你」、附一句邀请，都不足以证明联系成立。

真实的用户资料可来自用户明确对宠物的输入、请求与反馈，也可来自宿主实际可见的用户资料；范围不限于工作，也不要求用户每次使用斜杠命令或额外完成操作。用户说过、做过什么需要来源；不凭空写用户听了演奏、参与探险或作出回应。

宠物世界与宠物回应可以采用幻想表达，但建立关系的用户资料和交互必须真实。宠物的性格与独立生活继续保留，不能靠完全独立的虚构剧情替代用户联系。没有新资料时，可以回到尚有意义的真实输入及其后续影响；怎样避免重复见「故事类型」和「换装」。

### 每次检查都有宠物内容

2026-10-08，用户选择「每次都有宠物内容，长短由当次经历决定」。正常完成的每次五小时检查都应呈现当次宠物内容，不再因缺少新的用户事实且成长未到期而直接取消并留空。

长度由具体经历决定，不规定每次都写完整长故事。每次有内容不意味着每次都要改变状态、成长、换形象或配图；这些继续由故事和实际完成结果决定。内容仍须来自宠物世界，不能用检查报告或过程预告代替，也不能编造用户事实。

开发时需要一起调整 meta 的故事节奏、workflow 与 scheduling 的跳过分支，以及 output 的空白输出规则，避免不同文件仍要求相反行为。没有新用户资料时内容从哪里来，见「随机性、多样的宠物设计、可爱是前提」和「故事类型」。

### 它是用户养的宠物

2026-10-10，用户指出：之前的故事和讨论中的示例，都像宠物按自己的剧本在过独立的生活，不像一只「宠物」的活动。确认的逻辑：

- 领养了蛋之后，这只宠物就是用户在养的。
- 它有自己的家；它会和用户交互，会在家里活动，也会出门。
- 故事写的是一只被养着的宠物的生活，不是一个独立主角的冒险。

怎样表达（2026-10-10 确认）：

- 宠物陪在用户身边、困了、在等这类内容，用桌面上宠物形象的状态变化来表达，不靠文字描述。文字描述没有实感。
- 宠物给用户东西时，重点是把这样东西画出来交给用户，并写出宠物在想什么。这样更能体现关系和陪伴。
- 文字主要用来写宠物在想什么，不用来叙述图和状态已经表达的动作。

形象怎样换、要用多久，见「换装」和「形象生成和桌面更新」。画一样东西给用户只需要一张图。

交互方式（2026-10-10 确认）：

- 现在不做喂养，也不做其他照顾宠物的操作。
- 用户和宠物之间只有三种交互：默认的定时故事；用户和宠物对话；用户用命令强行调用（新故事、成长、重置、开始、停止）。起名和改名由 `/genpet` 接住，见[命令入口](#命令入口)。
- 各条命令做什么，见[命令入口](#命令入口)。`/genpet` 是总入口，和宠物对话用 `/genpet-chat`。
- 宠物的成长来自这三种交互里的真实内容和读到的用户资料。

每次检查的内容（汇总以上确认的内容）：

- 平常的一次检查，多数是一次换装。只换了样子、没有消息的检查也算有内容，最多配一句它在想的话。
- 宠物有东西要给用户时，画出这样东西，配上它在想的话。
- 有新的用户输入要回应、成长或孵化时，内容更完整。
- 内容以用户身边和它的家为中心，出门是其中一部分。领养旅程留下的线头、以前真实互动的后续，都可以用，由 Agent 选，用种子保证每次不同。
- `meta.md`「故事节奏」里「没有新东西就跳过」的规则，以及 `scheduling.md`、`workflow.md`、`output.md` 里取消故事、不发消息的分支，开发时按这里改。成长到期必须有故事这条不变。

### 什么决定每次内容的变化

2026-10-10 确认：

- 每次内容怎样变化，由这次的 context 决定：读到的用户资料、时间、宠物自己的记录（性格、关系、能力、家、给过的东西、以前的内容、领养旅程）。
- 用户对宠物说话不是常见的交互。用户说过的话只是 context 里的一项，和其他 context 一样使用，不单独设计「用户说话 → 宠物回应」的流程。
- 宠物不照搬用户在做的事。同样的 context，由这只宠物的性格和它与用户的关系决定它怎样变化。
- 对话不改变宠物。形象从更新到显示出来需要时间，做不到对话时当场变化；状态、形象和家仍然只由故事改变。
- 共同记忆落在三样东西上：它给过用户的东西、它家里留着的东西、用户对它说过的话。之后的内容可以回到这些旧东西上。现有记录已经能保存这三样，不加新的结构。

### 怎样让用户有期待

2026-10-10 确认。期待来自宠物自身正在发生的变化，下面四条是给 Agent 的参考：

- 成长之前有预兆。临近成长的几次检查里先让用户看到一点迹象，然后成长，成长之后留下痕迹。
- 它有一件正在做的事，跨几次检查慢慢推进，最后有一个结果。做完一件再换一件不同的。
- 它的能力慢慢长。设计里定下的能力一开始很弱，之后一点点变强。
- 不是每次都留悬念。Agent 对照最近的内容，避免每次用同一种结尾。

固定的只有弱交互：不提问、不邀请、不预告下次。

领养之后各种情况的手写示例见 [领养之后的内容案例](DAILY_CASES.zh-CN.md)。

### 故事类型

2026-10-10 确认。按用户看到什么变化来分，用来对齐设计和流程：

| 类型 | 用户看到什么 | 什么时候发生 | 要画什么 |
| --- | --- | --- | --- |
| 领养 | 最多 5 轮的选择旅程，最后得到蛋，附一段总结 | 领养时，只有一次 | 蛋的形象 |
| 成长 | 新阶段的形象，加一段比较完整的故事。孵化时它的家第一次出现 | Agent 判断积累够了，或到了最晚时间。共三次 | 整套新形象；孵化时加一张家的图 |
| 特殊形态 | 成年后换成一个特别的样子，过后变回来 | 成年以后，一周内进入，两天内结束 | 进入时画整套新形象；结束时复用原来的 |
| 换装 | 桌面上的它换了样子：穿的、戴的、拿的、正在做的事、姿势或身边的一点环境。最多配一句它在想的话 | 平常的检查，占大多数 | 整套形象；画过的直接复用 |
| 故事物件 | 以一样东西为关键来讲的故事：一张图，配它在想的话。东西不一定是给用户的，之后可以放进家里 | 故事里有一样值得看的东西时 | 一张图 |
| 家的变化 | 家的新样子 | 家里添了东西、整理过、搬家。隔了很久没有跑故事时，更多用家的变化来表达这段时间 | 一张家的图 |
| 只有文字 | 它直接对用户说的话，或者它在做的一件和用户有关的事 | 这次有一条和用户有关的 context 可以对应时 | 不画图 |

- 出门是故事发生的场合，和「在用户身边」「在家」并列，结果落在换装或故事物件上。
- 一个故事可以同时属于几类。
- 命令是触发方式：`/genpet-start` 触发领养，`/genpet-grow` 触发成长或特殊形态，`/genpet-story` 触发后三类。定时检查可以触发除领养以外的各类。对话不是故事。
- 运行时仍然先有故事，再由故事决定有哪些结果。不让 Agent 先选类型，也不设各类的比例。
- 只有文字的故事保留，因为每次都画图成本高。硬要求：内容必须能对应到一条和用户有关的 context（读到的用户近况、用户说过的话、以前一起经历过的东西）。对应不上时不能用这一类，改用看得见的类型。读不到用户资料时因此不会出现只有文字的故事。

怎样让类型和内容自然变化（2026-10-10 确认）：

1. 代码整理一份「最近的内容」交给 Agent：最近若干次各是什么类型、各类型上一次出现是多久以前、哪件事还没做完。类型从每次实际画了什么推出来，不加分类字段。
2. Agent 按这次的 context 想出几个候选故事，其中至少一个是看得见的类型。随机工具用种子选出一个，并按「最近的内容」加权：越久没出现的类型，机会越大。
3. 一条硬规则兜底，做法和成长的最晚时间一样：只有文字的故事最多连续 2 次，到了上限这次必须是看得见的类型。硬规则只留这一条。
4. 给 Agent 的参考：用户资料有新变化时，多用故事物件或它对用户说的话；没有新变化时，多用换装或把正在做的事往前推一步；隔了很久，多用家的变化；临近成长，用带预兆的换装。

### 换装

2026-10-11 确认。换装是平常检查里最主要的一类故事。之前的版本里状态形象的变化从来没有触发过。

换装指宠物看得见的样子换了，身体还是那个身体。范围是宽的：

- 穿的和戴的：衣服、帽子、围巾、首饰。
- 拿的和带的：手里、嘴里、背上的东西。
- 正在做的事：做事时的样子和用到的工具。
- 姿势和神情。
- 身边的一点环境：坐的东西、脚边的一盏灯、头顶的一小片雨。

这几样可以叠加，也可以只换一样，由 Agent 按故事决定，不设清单。

目标：用户每次打开电脑，先看到的是「它今天是什么样子」，并且对下一次的样子有期待。

设计原则：

1. 身体不变，认得出是它。身体本身变了算特殊形态。
2. 每次换装有来由。来由出自这次的故事：它正在做的事、时间、用户最近的 context、成长前的预兆。
3. 东西会留下来。它穿过、拿过的东西归它所有，以后可以再穿、换着搭，也可以放进家里。故事物件里出现的东西，之后可以被它戴上，再之后放在家里。
4. 小尺寸下看得出来。换的是轮廓和大色块，首饰这类小东西要画得够大。
5. 它自己换，用户不操作。用户说过的话仍然只是 context 的一项，可以影响之后的故事。
6. 可爱优先，不评价用户。
7. 整套重画。待机、走动和各个方向里它的样子一致。

示例，耳廓狐的一周：

| 时间 | 它的样子 | 来由 |
| --- | --- | --- |
| 周一 | 戴着一副护目镜 | 开始装那只小钟 |
| 周二 | 嘴里叼着一枚齿轮 | 这件事推进了一步 |
| 周三凌晨 | 披着小毯子打瞌睡 | 检查的时间 |
| 周四 | 脚边多了一盏小灯 | 用户最近常在深夜做事 |
| 周五 | 脖子上挂着装好的小钟 | 小钟做完了，变成它的挂坠 |

整套重画带来的结果：

- 每次新的换装都要画整套形象，用时按「形象生成耗时」的目标，15 分钟以内。这个目标因此每天都用得上。
- 复用画过的换装不用等。画过的越多，可以直接复用的越多。
- 一次检查里新的换装还在画的时候，桌面上保持原来的样子，画好并通过检查后再换上。

对应的测试用例：T1、T2（故事这边），V4（形象这边），S9、S13。

完成的标准：

- 代码能查的用例全部通过。

### 定时故事：测试发现的问题和现在的解决思路

2026-10-10 整理。问题来自 [工程问题记录](ENGINEERING.zh-CN.md)。

设计目标：

1. 每次检查用户都能感受到它，没有空白。
2. 内容由真实的 context 决定，和这位用户有关。
3. 它像一只被养的宠物，生活以用户身边和家为中心。
4. 每次不一样，并且让用户对后面有期待。
5. 用户看到的只有宠物的内容，没有过程和机制。
6. 复用画过的形象时检查很快完成；画一套新的形象在 15 分钟以内。

| 测试发现的问题 | 解决思路 | 状态 |
| --- | --- | --- |
| 状态形象的变化从来没有触发过。它是平常检查里最主要的一类故事 | 换装作为主要的故事类型来做：故事决定它换成什么样，整套重画，换到桌面上。故事和形象两边都测，见「换装」和用例 V4 | 已定，待开发和实测 |

| 故事像宠物自己的独立剧本 | 写被养的宠物；同样的 context 由性格和关系决定它怎样变化 | 已定，待开发 |

还没有解决思路的三处：

1. 过程文字是从哪里来的。要先查清是定时任务的提示词写法引起的，还是 Agent 运行时自己加的，才能决定怎样去掉。
2. 状态变化之后，桌面上是否真的显示出来。原则已定，见「桌面更新的可靠性」：在开发时保证桌面会更新，运行时不做超出范围的验证。
3. 定时运行里能读到多少用户资料，决定了内容能和用户有多少联系。

### 用户看到的文字和定时检查的节奏

2026-10-10 确认目标和设计原则。具体做法由开发时决定。

测试里发现的问题：定时检查时对话里出现「我会看看小家伙……」这类过程文字；定时任务的名称和说明里写着执行要求；用户确认成长之后，回复里又解释了一遍技能条款。

目标：用户能看到的每一处文字都是体验的一部分，包括会话名称、任务名称、任务说明、过程中的消息、通知、最终内容和命令确认。

设计原则：

1. 用户看到的只有宠物的内容。过程、工具、检查结果都不出现。
2. 执行要求放在后台读取的文档里，可见的文字里不写。
3. 没有要说的就不说。只有状态变化的检查没有消息。
4. 需要用户确认时，用一句直接的话说清将要发生什么，不解释规则。
5. 用户问的是找不到、不显示这类问题时，用直接的说明回答，不用宠物的口吻。
6. 用户每次打开电脑，当天至少能看到它一次变化。定时检查在电脑关着时不触发，靠开机后补一次检查还是别的办法，开发时实测后定。
7. 定时任务所在的那个对话，名称是 GenPet 或另一个定好的名字。只管这一个对话，用户在别的对话里用到 GenPet 命令时不改那个对话的名称。Codex 会按上下文自动更新会话名称，在 skill 里写明规则，让 Codex 把名称定成这个名字。能否做到要在开发时实测。

开发时先要查清的：过程文字是定时任务的提示词写法引起的，还是 Agent 运行时自己加的；开机后 Codex 会不会立刻触发过期的定时任务；skill 里的规则能否让 Codex 把会话名称定成指定的名字，名称会不会在后面的对话里又被改掉。

对应的测试用例：S10、S14、S15、S16、S17，见 [测试用例](TEST_CASES.zh-CN.md)。

### 图片的展示

2026-10-11 确认目标和设计原则。

测试里发现的问题：同一张图在对话里出现两次，画图工具已经自动展示了一次，最终回复里又嵌了一次；审核用的预览图也出现在对话里。

目标：图是用户看到的内容的主体。每张图都有它要传达的东西，用户看到的图不多也不少。

设计原则：

1. 一张图在对话里只出现一次。
2. 用户只看到最终采用的图。画图过程里产生的图片，包括候选、审核用的预览、各个动作的源图和整套动作的拼图，都不在对话里出现。画图交给 subagent 去做，主对话里只呈现最后的结果。
3. 成长和进入特殊形态时，消息里带一张它新样子的图。对话里因此留下它每个阶段的样子。
4. 图画的是故事要传达的那样东西：故事物件只画那样东西，家的变化画家。它不是给文字配的插图。
5. 图的风格和这只宠物一致，可爱优先。
6. 一条消息通常只有一张图。孵化那次有两张：它的新样子和它的家。

开发时要实测：画图交给 subagent 之后，subagent 里工具自动展示的图会不会仍然出现在主对话里。

对应的测试用例：S21、S22、S23。

## 成长和特殊形态

2026-10-10 确认目标和基本设计原则。具体做法由开发时决定。

成长的目标：

- 用户看得出它在长大，并且觉得是自己养大的。
- 成长一定会发生，用户不需要做任何操作。
- 成长之前有预兆，成长之后留下痕迹。
- 它长成什么样，和这位用户有关。
- 成长不让用户久等，也不因为画图失败而推迟。

成长的设计原则：

- 阶段顺序固定：蛋、幼年、少年、成年，一次只前进一个阶段。
- 成长由经历和最晚时间共同决定，见下面「和用户一起成长」。
- 长成什么样由基因、memory 和这段时间的 context 决定。
- 每个阶段在身体、能力和说话方式上都有看得出的不同。
- 长大以后仍然认得出是同一只宠物。

和用户一起成长（2026-10-10 确认）：

宠物记录分成 soul、memory 和现在的样子之后，成长有三层：身体（到成年就停）、能力（到成年基本长完）、它记得的事和与用户的相处（memory，一直在变）。

目标：用户觉得它是和自己一起长大的。它的每一次变化，都对得上自己这段时间真实发生的一件事；回头看，它记得的就是两个人一起过的这段时间。

设计原则：

- 经历就是 memory 有了新内容。一次故事之后 memory 被重写了，就算一次经历，不另设一套判断。
- 成长的时机尽量落在用户真实的节点上。经历攒够以后，在哪一次成长由 Agent 选；context 里出现用户的一个真实节点时，就在那一次。
- 成长那一次的内容从 memory 里来：写它自己的变化，再带上用户这段时间一件真实的变化。只陈述，不评价用户。
- 身体长到成年就停，memory 不停。成年以后的变化来自 memory：它对用户说话的方式变了，它会提起旧事，家里留着一起经历过的东西。
- 成长不做成数值。用户看不到进度条、等级、亲密度，只看到它变了。

成长的规则：

- 这个阶段里经历满 5 次之后，Agent 选一次成长。5 是起始值，模拟后再调。
- 到了最晚时间必须成长：幼年和少年各一周。
- 蛋在领养后 5 小时孵化。孵化的时候请用户给它起名，只请这一次。`/genpet-grow` 可以强行成长。
- 插件升级不换宠物：一只宠物一个 ID，形象走 Codex 的 cloud ID 多端同步，升级前后都是同一只。升级前已经领养的宠物没有领养旅程和 memory，memory 按它已有的故事补写一次，经历从升级时开始数。
- 定时检查只在电脑开着时触发。按这个规则，一个阶段最短两三天，最长一周。
- 用户不在的时候到了最晚时间，回来后的第一次检查成长，没有预兆，内容把这段时间一并写进去。

要避免的做法：让用户去攒数值；把用户做的事原样复述；每次成长都是同一套写法；memory 写成流水账。

特殊形态的目标：

- 成年以后它仍然会变，用户一直有新东西可看。
- 它是暂时的，会变回来，变回来之后留下痕迹。

特殊形态的设计原则：

- 和换装分开：身体本身变了样才算特殊形态；穿的、戴的、拿的、姿势和神情变了是换装。
- 可爱优先。它不是对用户习惯的评价，不拿熬夜、加班这类内容作起因。
- 不成为套路：画过的可以再出现，也可以有新的，由 Agent 和种子决定。
- 时间由最晚时间保证：成年后一周内进入，进入后两天内结束。只在成年出现。

代码现在已经保证的部分见 `src/growth.ts`、`src/lifecycle.ts`：阶段顺序、最晚时间、特殊形态只在成年、成长和进出特殊形态都必须换形象。

做法参考，开发时决定是否采用：临近成长时，在出现预兆的那几次检查里先把下一阶段的形象画好，到点直接换上。这样到了最晚时间不用再等画图，画失败也不会推迟成长。

随之要改的现有内容：`meta.md` 里特殊形态的写法是「用户长期加班、熬夜引出黑化、中毒」，要按上面的原则改掉。换装和特殊形态的分界、成长的规则，也按这一节和「换装」写进 `meta.md` 和相关提示词。

每个阶段变什么（参考）：

| 阶段 | 最晚持续 | 身体 | 能力 | 说话 | 家 |
| --- | --- | --- | --- | --- | --- |
| 蛋 | 5 小时 | 字面的蛋，壳上有领养旅程留下的线索 | 没有 | 不说话 | 没有 |
| 幼年 | 一周 | 没长开，来源的特征只露出一点 | 很弱，常常做不成 | 只有一两个简单的词的想法 | 孵化时建立 |
| 少年 | 一周 | 特征长出来了 | 能用 | 说整句话 | 继续变化 |
| 成年 | 不再成长 | 完整 | 完整 | 说整句话 | 继续变化；可以进入特殊形态 |

## 形象生成和桌面更新

目标：画一套新的形象在 15 分钟以内；换了之后桌面上真的更新。成长、特殊形态和换装都用到这两条。

对应的测试用例：V1 到 V4、U3，以及 Dots 的 D1。

### 形象生成耗时

2026-10-10，用户确认要做工程优化：

- 目标：换一次完整形象控制在 15 分钟以内。最早的版本做到过。
- 2026-10-11 补充：换装也整套重画，见「换装」，所以这个目标不只用在成长上，平常的检查也用得上。
- 减少过度的测试，去掉没有必要的约束检查。
- 尽可能并行执行。

依据是 [2026-10-05 的耗时调查](research/growth-latency-20261005.md)：那次成长用了约 54 分钟，图像服务本身只占约 9 分钟，其余是 Agent 的判断、审核、文件处理和串行交接。无返工时只需要生成 13 次，实际生成了 26 次。

| 阶段 | 那次耗时 | 主要问题 |
| --- | ---: | --- |
| 故事准备、基准形象 | 6 分 | |
| 九种普通动作 | 7 分 | |
| 方向姿势（四方向参照、16 个方向、返工） | 33 分 | 三步串行；方向反复画错；尺度和透明化问题发现得晚 |
| 组装、验证、独立审核 | 6 分 | 多轮审核 |

做法（2026-10-10 确认，开发时实测）：

1. 并行。基准形象通过后，九种动作和两组方向姿势同时生成，去掉「四方向参照 → 第一组 → 第二组」的串行依赖。
2. 方向姿势只画一侧，另一侧由代码左右翻转得到。生成次数减半，也不会再把右下画成左下。身体左右不对称的宠物是否适用，开发时实测。
3. 提取、统一大小、背景透明、组装这些确定的处理写进运行时代码，由代码检查尺寸和格式，不再由 Agent 逐项审核。
4. 看图的检查保留两次：基准形象一次（后面都依赖它），组装好的整套形象在实际显示大小下一次。每张源图的单独审核和重复的独立审核去掉。
5. 同一个错误出现两次就换做法；一行重画有次数上限。到上限仍没通过时，先用基准姿势补上那几格，让这次更新按时完成。
6. 改完后实测耗时，分开记录生成、处理、审核和交接各用了多久。

### 桌面更新的可靠性

2026-10-11 确认原则：

- 形象换了之后桌面要真的更新。这件事在开发时做好并测试，不留给插件运行时去补救。
- 插件运行时不做超出范围的动作去验证显示，例如 Computer Use。
- 内部接口能给出状态时可以用它。

## 宠物记录的结构：soul、memory 和 state

2026-10-10 确认：借鉴 Agent 设计里 soul 和 memory 的分法，把宠物记录里的 `pet` 分成几块。用户同意为此重构记录。

讨论的起因：Dots 要按宠物和用户的关系说话，而性格是领养时定的，装不下后来的相处。关系属于 memory，不单独设字段。

```
pet
  id、name、naming、adoptedAt、revision、Avatar ID   身份，由代码管理
  soul    { genes, personality, acquisition }        它是谁
  memory  { text, updatedAt, storyId }               它记得什么
  state   { stage, description, home, special }      它现在的状态
```

| 块 | 内容 | 谁写、什么时候写 | 代码保证什么 |
| --- | --- | --- | --- |
| soul | 基因、性格（含拟声词和说话习惯）、领养的来由 | GeneDesigner，领养时 | 写入后保持不变。旧宠物缺的部分可以补一次 |
| memory | 一段短文字：它和用户之间发生过的重要的事，现在怎样和用户相处 | StoryDesigner，故事完成时。有值得记住的真实互动才重写，没有就不动 | 只在 `finish-story` 写入 |
| state | 阶段、当前状态的描述、家、特殊形态 | StoryDesigner 和 HomeDesigner，每次故事完成时 | 现有规则：阶段只向前，到期必须成长 |

名字由用户给，可以改，所以放在身份里。起名和改名由 `/genpet` 接住。第三块叫 `state`，沿用现有的 `pet.state`：它现在已经保存当前状态的描述，把阶段、家和特殊形态也归进来。

这里的块名和字段名（`soul`、`memory`、`state` 以及各块里的字段）都是暂定的。2026-10-10 用户确认：命名在开发时统一优化一遍，和「开发阶段待办：字段名与提示词措辞」一起做。现在定下来的是分成哪几块、每块放什么、谁在什么时候写。

memory 的规则：

- 领养时写第一段：领养旅程里发生的事，和这只宠物与用户关系的出发点。
- 每次是重写。旧的内容合并或放下，长度由 Agent 控制，保持短。
- 只记真实发生的。用户说过什么、做过什么要有来源；敏感和隐私内容不记。宠物自己在故事里的经历可以记。
- memory 每更新一次，算宠物的一次经历，经历攒够了它会成长，见「成长和特殊形态」。所以只在有值得记住的事时才重写；写得太勤，它会长得太快，memory 也会变成流水账。
- 记的是它和用户之间的事。对用户本人的了解继续优先用 Codex 的用户记忆，见「读用户资料」。
- 故事和对话摘要照旧完整保存，memory 是它们的总结。宠物养了几个月后，早期的相处仍然留在 memory 里。

三处读同一份记录：写故事和对话时读 soul、memory 和 state；Dots 用的宠物简介由代码从这三块里摘出来。

选这个结构的理由：

1. soul 写入后不变这条规则，可以在代码里一个地方保证。
2. 三块和子 skill 一一对应：GeneDesigner 写 soul，StoryDesigner 写 memory 和 state。
3. 宠物简介就是这三块加上名字。

开发时：

- 记录版本从 2 升到 3。旧记录保持可读，读取时把原来平铺的字段归到三块里。
- 和「开发阶段待办：字段名与提示词措辞」里的改名一起做，只做一次旧记录兼容。
- 故事计划（`plan-story` 的输入）增加 memory，和 `home` 一样：有新的才带上。
- 随之要改 `src/model.ts`、`lifecycle.ts`、`status.ts`、`storage.md`、`units.json` 和相关测试。

## 命令入口

2026-10-11 确认目标和设计原则。

现在有 9 个命令：`/genpet`、`/genpet-start`、`/genpet-stop`、`/genpet-story`、`/genpet-grow`、`/genpet-name`、`/genpet-reset`、`/genpet-switch`、`/genpet-debugger`。已定新增 `/genpet-chat`。菜单里「GenPet」和「genpet」重复出现。

目标：用户只需要记很少的命令。大多数事情用自己的话说，由 `/genpet` 接住。

设计原则：

1. `/genpet` 是总入口，用户说什么由 Agent 判断去做哪件事。
2. 单独的命令留给三类：会改变宠物的动作、需要明确入口的对话、调试工具。
3. 会替换宠物的命令先确认再做。
4. 命令说明写的是实测能做到的事。
5. 菜单里每个入口只出现一次。

| 命令 | 做什么 | 处理 |
| --- | --- | --- |
| `/genpet` | 总入口 | 保留 |
| `/genpet-start` | 领养，或接着养并打开定时检查 | 保留 |
| `/genpet-chat` | 和宠物对话 | 新增 |
| `/genpet-story` | 立刻来一次内容 | 保留 |
| `/genpet-grow` | 强行成长或进入特殊形态 | 保留 |
| `/genpet-stop` | 停掉定时检查 | 保留 |

## 初始化检查、领养新宠物和多只宠物

2026-10-11，用户补充三条需求：

1. GenPet 初始化时先检查既有环境，把查到的情况告诉用户，和用户确认是否清理后再初始化。
2. 用户领养新宠物时也要先和用户确认。
3. 要考虑用户有多只 GenPet 的情况：数据怎样管理、怎样同步、怎样切换。

用户同时确认：下面每一条开发时都要测试。

现在的做法：一个环境只有一只宠物。`/genpet-start` 在没有宠物时领养，有宠物时接着养；`/genpet-reset` 备份旧记录，新宠物接手原来的 Pet 条目。初始化时不检查 Codex 里已有的 Pet 条目、云端 Pet 和定时任务。

### 已确认的做法

2026-10-11 确认：

- **唯一激活一只宠物。** 定时故事只写给激活的这一只。其他宠物留在记录里，没激活的时候成长的最晚期限不计时。
- **哪只是激活的，以用户在 Codex 里选中的为准。** 开发时先试能否读到当前选中的 Pet 的 ID，并对应到 GenPet 的宠物 ID。选中的 ID 可能是本地的 `custom:` 条目，也可能是它的云端 `pet_` ID，两者是同一只。定时故事和斜杠命令都按这个 ID 找宠物，不靠名字，避免搞混。
- **清理的原则是不搞乱。** 默认保留云端 Pet；旧版本留下的东西不影响新版本和新的宠物；清理时把留下的内容告诉用户，过程透明。
- **记录按宠物分目录。** 每只宠物一个目录。切换激活的宠物不用搬数据；[切换主环境](#开发需求)时搬的是一只宠物的整个目录。
- **「换掉现在这只」和「再养一只」是两件事。** 换掉：旧记录进备份，新宠物接手原来的 Pet 条目和 cloud ID，Dots 里不用重新选。再养一只：新建 Pet 条目和 cloud ID，原来那只保持原样。用户提出时，先把两种做法各自的结果讲清楚，得到用户确认后才开始。

激活的宠物这条，开发时要定的细节：

- 一篇故事开始时确定它属于哪只宠物，之后的每一步都按故事里记的宠物 ID 做。故事写到一半用户改选了别的宠物，这篇故事仍然完成在原来那只上。
- 用户选中的不是 GenPet（内置 Pet 或别的自定义 Pet）时怎么办。起始做法：沿用 GenPet 上次激活的那只，保持用户的选择不动。
- 读不到选中项时怎么办。起始做法：沿用上次激活的那只，并在结果里说明没有读到。
- 用户说「切换到另一只」时，由 GenPet 在 Codex 里选中那一只的 Pet，再以它为激活的宠物。
- Dots 里同理：Dots 选中的是哪个 cloud ID，用的就是哪只宠物的形象和简介。

### 和其他部分的关系

- M7 里「Codex 里选中它的 Pet」这一步：用户实测直接切换到指定 ID 的宠物做不到，见[宿主能做到什么](#宿主能做到什么)。开发时复测；仍做不到时，这一步改成告诉用户在 Pet 设置里选哪一个。
- M1 的检查和[诊断](#加载缺失与显示异常的诊断和修复)用的是同一套只读检查，对应架构里的 `diagnose`。
- M5 的目录结构和[宠物记录的结构](#宠物记录的结构soulmemory-和-state)一起做，记录版本只升一次。
- M6 依赖 D1（把新形象换到云端 Pet）。宠物简介如果能写进 Pet 条目的 `description`（D5），每只宠物的简介就自然跟着它自己的 cloud ID 走。

## 加载、缺失与显示异常的诊断和修复

2026-10-11 按目标和设计原则整理，并记录用户的实测结果。方向在 2026-10-08 已确认，这次没有改变。

2026-10-08，用户提出「加载我的 genpet」，实际需求是：宠物没有显示在桌面上，并且在 Codex 的 Pet 设置里也找不到。Agent 当时只读取宠物记录、展示已有图片，并用「我在这儿」等宠物对白回应，没有执行客户端加载或确认故障；用户明确要求技能支持此类诊断和修复。本次先记录需求，尚未实现。

目标：用户说找不到、不显示、加载不出来时，得到一个查过之后的直接回答：现在是什么情况，做了什么，还有哪一步要用户自己做。

设计原则：

1. 先查再答。Agent 从用户的话和上下文判断这是在报故障，先查 GenPet 和 Codex 两边的情况再回应。用户不用记专用命令。
2. 用直接的说明回答。宠物的口吻留给陪伴和故事。
3. 修的是同一只宠物：同一个 ID、同一份记录。修复过程不领养、不重置、不推进成长、不重画形象。
4. 四件事分开说：Pet 列表里有没有它、当前选中的是不是它、刷新请求有没有送到、桌面上实际有没有显示。查不到的那一项就说查不到。
5. 只用宿主接口、app-tools、IPC 和插件运行时。
6. 修复只做实测可靠的动作。接口做不到的，告诉用户要自己做的那一步，只说这一步。

### 宿主能做到什么

用户的实测结果（2026-10-11 记录）：

| 动作 | 结果 |
| --- | --- |
| 更新同一个 ID 的宠物的形象 | 可以 |
| 直接切换到指定 ID 的宠物 | 做不到 |
| 直接让宠物显示或隐藏 | 还没测，开发时实测 |

2026-10-05 的工程记录里有一条相关现象：用 `switch-pet` 选中本地 ID 后，读回来是这个 ID，客户端随后又按迁移映射恢复成云端 ID。见 [工程记录](ENGINEERING.zh-CN.md)。

对设计的影响：

- 换形象、成长、特殊形态都靠更新同一个 ID 的宠物来实现，整个设计不依赖切换。
- 当前选中的是别的 Pet 时，修复告诉用户在 Codex 的 Pet 设置里选哪一个，写出它在列表里的名字（`genpet-xxxxxx`）。
- 桌面上没有显示、接口又不能直接让它显示时，告诉用户怎样打开。
- `/genpet-switch` 现在的说明写的是立即切换，与实测不符。开发时再测后定，见[命令入口](#命令入口)。
- [多只宠物](#初始化检查领养新宠物和多只宠物)的 M7：GenPet 这边改「当前在养的是哪只」可以做到；让 Codex 选中它这一步，按现在的实测要用户自己做。

开发时要实测：

- 用云端 ID 切换能不能成功，结果会不会被客户端改回去。
- 有没有接口能直接让宠物显示或隐藏，能不能读到它当前是否显示。
- 每个修复动作做完后，四件事里哪几件能从接口读回来。

### 2026-10-08 的排查结果

本地宠物 `genpet-d2aa92aa-6e9d-472e-8b72-6142a967580f` 映射到云端 `pet_6ac34cd611a481918fc40da68ff4972a`；云端列表仍有 `genpet-d2aa92`，客户端选中 ID 也一致。后续重新写入该选择并读回一致，云端列表缓存刷新请求已转发。未确认用户所见列表缺失的原因，也未确认桌面实际显示；这些结果不能记为故障已修复。

### 验收

用户用自己的话报故障，例如「加载我的 genpet」「桌面上不显示，设置里也找不到」：

- Agent 先查，再按查到的情况处理，最后分开说明四件事。
- 宠物的 ID、记录、成长阶段和形象在修复前后一致。
- 接口做不到或查不到时，回答里写明是哪一项，并给出用户要做的那一步。
- 回答里没有宠物的对白，也没有聊天图片。

## Dots 联动

2026-10-10，用户实测后确认方向。之前让 Dots 自己生成和换形象的做法没有走通，见 [测试记录](evidence/README.md) 里 2026-10-03「Dots 分离方案走不通」一条。

### 实测结果

在 Codex 桌面端正常生成 GenPet 并取得 cloud ID 后，Codex 自动同步这只 Pet。在 Dots 里选择这个 ID 的 Pet 就能用。

### 目标

桌面端和 Dots 之间有联动，Dots 有它特别的体验。下面三条是用户提出的思路。实现时可以采用别的技术方案，以达到这个目标为准。

1. 同一只宠物靠 cloud ID 在两边同步。
2. Dots 可以变成用户领养的这只 GenPet：用它的形象，按它的说话风格说话。Dots 原有的功能保持不变。
3. 故事默认由桌面端 Codex 驱动，可以切换到 Dots。宿主、skills、运行时这一套在两个环境各有一份，用户选其中一个作为主环境。

### 宠物的说话风格

2026-10-10 确认：宠物有自己的说话风格，包括拟声词、说话方式等。它来自宠物记录里的两部分，见[宠物记录的结构](#宠物记录的结构soulmemory-和-state)，不另设字段：

- 拟声词和基本的说话习惯写在 soul 的性格里，领养时定下来。
- 对用户说话的亲疏和语气来自 memory，随着它和用户的相处变化。

用在三处：用户和宠物对话；故事里宠物说的话和想的事；Dots 变成这只宠物后的回复。

Dots 变成这只宠物后怎样说话，原则是 Dots 的功能照常：

| 阶段 | Dots 怎样说话 |
| --- | --- |
| 蛋 | 和原来一样，只换了形象 |
| 幼年 | 回复的开头或结尾加一个短的拟声词，工作内容一个字不动。开发时写样本给用户看了再定 |
| 少年和成年 | 按这只宠物的性格，和它与用户现在的相处来说话 |

边界：

- 说话风格只用在 Dots 对用户说的话里。Dots 替用户产出的东西保持原样：代码、文档、提交说明、替用户发出的邮件和消息。
- 工作内容完整、准确。性格只体现在语气上，Dots 照常接任务、照常完成。
- 用户很久没来时，宠物可以注意到时间过去了，Dots 的语气保持友好。

随之要改的现有内容，留到开发阶段：性格单元（`personality.md`、`units.json`）增加拟声词和说话习惯；`meta.md` 的「个体性格」「对话」和 `chat.md` 改为按性格和 memory 说话；`storage.md` 里性格「包含怎样对待用户」的说法改为只表示领养时的出发点；已有的宠物按现有性格和故事补上说话习惯和 memory。
