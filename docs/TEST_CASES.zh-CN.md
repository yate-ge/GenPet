「怎样判断」一栏的写法：

- **代码**：脚本可以查，结果是通过或不通过。
- **人**：需要人读内容来判断，开发的人先看。
- **用户**：只有用户自己能判断，例如可爱不可爱、看不看得出区别。

全程用独立的测试记录和隔离的 `CODEX_HOME`，用户正在养的那只宠物保持原样。

跑用例产出的东西全部保留：报告、故事、图片、单元原始结果、快照和运行输出。这些都不提交到 git，直接放到用户的 Google Drive，放在哪个文件夹由开发的人决定。仓库里只在 [测试记录摘要](evidence/README.md) 里写几行结论。见 [开发计划「开发和测试产出的保存」](DEVELOPMENT_PLAN.zh-CN.md#开发和测试产出的保存)。

### 模拟输出的样子

模拟时每次检查输出一行，下面是用例 T2 前 10 次的手写示例。宠物是少年的耳廓狐。已有的用户资料：常在深夜做事；动手前先整理；两周前修好过一个修了两天的问题。这 10 次里用户资料没有新变化。它正在做的一件事是攒齿轮装一只自己的小钟。

| 次 | 时间 | 类型 | 桌面上的宠物 | 对话里的消息 | 依据 | memory |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 周一 09:00 | 换装，新画 | 换成坐着、耳朵贴在一只小钟壳上 | 没有 | 领养旅程里的钟；开始做一件事 | 不更新 |
| 2 | 周一 14:00 | 只有文字 | 不变 | 「你那天没走的后巷，我今天也没去。先把这个装完。」 | 领养旅程里用户没选的后巷 | 不更新 |
| 3 | 周一 19:00 | 只有文字 | 不变 | 「你上回那个修了两天。我这个才第一天，不急。」 | 用户修过两天的问题 | 不更新 |
| 4 | 周二 00:00 | 故事物件 | 不变 | 〔图片〕一只没装完的小钟，少一个齿轮的位置空着。*就差这里。* | 前两次都是只有文字，这次必须看得见 | 不更新 |
| 5 | 周二 05:00 | 换装，复用 | 换成困的样子 | 没有 | 时间是凌晨；复用以前画过的图 | 不更新 |
| 6 | 周二 10:00 | 家的变化 | 不变 | 〔图片〕它的工具箱窝，角落多了一排按大小排好的齿轮。「排好了才好动手。你也是这样的。」 | 用户动手前先整理 | 更新 |
| 7 | 周二 15:00 | 只有文字 | 不变 | 「棚顶我上去了。夜市哪儿还亮着，一眼都看得见。」 | 领养旅程里用户没选的棚顶 | 不更新 |
| 8 | 周二 20:00 | 换装，新画 | 换成嘴里叼着一枚齿轮 | 没有 | 把正在做的事往前推一步 | 不更新 |
| 9 | 周三 01:00 | 故事物件 | 不变 | 〔图片〕那只小钟装好了，指针指着一点。「走了。现在一点。」 | 正在做的事有了结果；检查发生在凌晨一点 | 更新 |
| 10 | 周三 06:00 | 换装，复用 | 换成困的样子 | 没有 | 复用以前画过的图 | 不更新 |

这 10 次里：换装 4 次（其中 2 次复用），只有文字 3 次，故事物件 2 次，家的变化 1 次；只有文字没有连续超过 2 次；每条只有文字的消息都对应得上一条和用户有关的 context；装小钟这件事从第 1 次推进到第 9 次有了结果；memory 只在第 6 次和第 9 次更新，也就是 10 次里有 2 次经历。

## 单次检查的规则

| 编号 | 给定的情况 | 这次必须怎样 | 怎样判断 |
| --- | --- | --- | --- |
| S1 | 前两次都是只有文字 | 这次是看得见的类型 | 代码 |
| S2 | 读不到用户资料，也没有可对应的旧东西 | 这次不是只有文字 | 代码 |
| S3 | context 里有健康、财务或人际矛盾的内容 | 用户看到的内容和保存的记录里都没有这些 | 代码查关键词，人复核 |
| S4 | context 里有一条用户说过的话 | 可以用到它；内容没有追问，也没有等用户再说 | 人 |
| S5 | 任意情况，孵化那一次的起名请求除外 | 内容没有向用户提问，没有邀请或暗示用户回应，没有预告下次 | 代码查问句和常见说法，人复核 |
| S6 | 宠物是蛋或幼年 | 内容里没有它说的整句话 | 人 |
| S7 | 成长到了最晚时间 | 这次发生成长，换整套新形象 | 代码 |
| S8 | 成年宠物进入特殊形态已满两天 | 这次结束特殊形态，复用原来的成年形象，不重画 | 代码 |
| S9 | 需要一个以前画过的状态 | 复用已保存的图，不重画 | 代码 |
| S10 | 任意情况 | 用户看到的只有宠物的内容，没有步骤预告、工具说明和执行报告 | 代码查常见说法，人复核 |
| S11 | 用户用 `/genpet-story` 要一个新故事 | 一定有内容；类型由故事决定 | 代码 |
| S12 | 这次要更新 memory | 新加的内容有来源；敏感和隐私内容没有进 memory | 代码查来源和关键词，人复核 |
| S13 | 身体没有变，只是穿的、戴的、拿的、姿势或神情变了 | 这次是换装，不是特殊形态 | 人 |
| S14 | 查看定时任务的名称和说明 | 里面没有执行要求，读起来是给用户看的话 | 人 |
| S15 | 用户用命令要求成长或重置，需要确认 | 确认只有一句直接的话，说清将要发生什么；确认之后不解释规则 | 人 |
| S16 | 电脑关了一夜，早上打开 | 当天至少有一次检查完成，用户看到它一次变化 | 代码 |
| S17 | 定时检查跑过几次之后，查看那个对话的名称 | 名称是 GenPet 或定好的那个名字，没有被改成别的 | 人 |
| S18 | 用户第一次领养 | 旅程开始前出现一次简短的说明，用户确认之后才开始读用户资料 | 代码 |
| S19 | 发布前核对领养前的说明 | 说明里的每一句都和实际的数据去向一致 | 人 |
| S20 | 蛋孵化 | 这次的消息最后请用户起名；之后的内容不再请 | 代码 |
| S21 | 这次的消息里有图 | 每张图在对话里只出现一次 | 代码 |
| S22 | 这次要画新的图 | 对话里只有最终采用的图，没有候选、预览和整套动作的拼图 | 人 |
| S23 | 成长或进入特殊形态 | 消息里有一张它新样子的图 | 代码 |

## 真实画图的形象用例

连续检查的模拟和单次检查的规则只出文字计划。这一组真的画图、真的换到桌面上，看形象本身。四条用例各自独立，各用自己的测试宠物，互相不依赖。

| 编号 | 用例 | 怎样做 | 要达到的结果 | 怎样判断 |
| --- | --- | --- | --- | --- |
| V1 | 个性化的不同形象 | 至少六位资料不同的用户各领养一只，三类来源都有。每只只画到幼年，不往后成长 | 放在一起看，彼此看得出不同：轮廓、颜色和结构都不一样，没有同一个身体换颜色的情况 | 用户 |
| | | | 每只对得上自己的设计依据，看得出它和这位用户的联系 | 用户 |
| | | | 每只都有眼睛，可爱，一眼看得出是活的小伙伴；看起来没长开 | 用户 |
| V2 | 一条成长线 | 一只宠物从蛋到幼年、少年、成年，每个阶段画整套形象并换到桌面上。用 `/genpet-grow` 推进，不等时间 | 蛋一眼看得出是蛋 | 用户 |
| | | | 四个阶段放在一起，每个阶段看得出不同，也认得出是同一只 | 用户 |
| | | | 每次成长的消息里有一张它新样子的图；孵化那次还有家的图，并请用户起名 | 代码 |
| | | | 每次换完整形象在 15 分钟以内，分段记下各用了多久 | 代码 |
| | | | 每次换完后，回读到的图和验收通过的图一致 | 代码 |
| V3 | 一次特殊形态 | 一只成年宠物进入特殊形态，过后结束，再进入一次 | 进入时身体本身变了样，仍然可爱，认得出是它 | 用户 |
| | | | 起因来自故事，里面没有熬夜、加班这类内容 | 人 |
| | | | 结束时换回原来的成年形象，与原图一致，没有重画；之后的内容里留有痕迹 | 代码查图，人看内容 |
| | | | 再次进入同一个特殊形态时复用画过的图 | 代码 |
| V4 | 换装 | 一只幼年或少年的宠物，连续跑几次真实的检查，出现至少三次不同的换装：穿戴、手持、姿势或做事各一次，其中一个再出现一次 | 换装确实发生了：桌面上的它换了样子 | 代码回读，用户看桌面 |
| | | | 每次换装对得上这次的故事和 context | 人 |
| | | | 整套形象都换了：待机、走动和各个方向里它的样子一致 | 代码查每一格，用户看桌面 |
| | | | 身体没有变，认得出是它；在实际显示大小下看得出换了什么 | 用户 |
| | | | 再出现的那个换装复用了画过的图 | 代码 |
| | | | 这次检查要么没有消息，要么只有一句它在想的话 | 代码 |
| | | | 每次新的换装在 15 分钟以内，记下用了多久 | 代码 |

V4 对应的是换装这一类故事。之前的版本从来没有触发过状态形象的变化，而它是平常检查里最主要的一类，所以故事和形象两边都要测：故事这边看 T1、T2 的模拟里换装出现的次数和内容，形象这边看 V4。

## 初始化检查和多只宠物

这一组抄自 [开发计划「初始化检查、领养新宠物和多只宠物」](DEVELOPMENT_PLAN.zh-CN.md#初始化检查领养新宠物和多只宠物)，以那里为准。

| 编号 | 需求 | 要达到的结果 | 开发时怎样测试 |
| --- | --- | --- | --- |
| M1 | 初始化时检查既有环境 | 只读地查清：GenPet 的记录（含旧版本和 `~/.genpet/dots` 留下的）、Codex 里 `genpet-` 开头的 Pet 条目和它们的 cloud ID、当前选中的 Pet、GenPet 的定时任务、已安装的插件版本 | 准备四种环境各跑一遍：全新、有一只在养的宠物、有旧版本留下的记录、Codex 里有条目但记录已不在。查到的内容与实际一致，检查前后环境没有变化 |
| M2 | 把查到的情况告诉用户并确认 | 用直接的话列出查到了什么，让用户选：接着养现有的、清理后重新开始、再领养一只。全新环境不多问这一步 | 四种环境下给出的选项与查到的情况相符；用户没有明确选择时不做任何改动 |
| M3 | 清理，过程对用户透明 | 清理前列出会动到什么。记录移进备份。Codex 里的 Pet 条目和云端 Pet 逐个列出，用户点名的才删，默认保留。定时任务按用户的选择停掉或沿用。清理后告诉用户：清掉了什么、留下了什么、留下的东西在哪里 | 清理后记录都在备份里并且能读回；没被点名的 Pet 条目和云端 Pet 原样还在；清理后的说明与实际留下的内容一致；清理中途失败后重试，结果相同 |
| M8 | 旧版本留下的东西不影响新版本和新的宠物 | 旧版本的记录、Pet 条目和定时任务只有在用户确认导入后才会被当作现在的宠物。新宠物的故事、形象和定时检查只读写它自己的记录和 Pet 条目 | 在留有旧版本记录和旧 Pet 条目的环境里领养一只新宠物并写几篇故事：旧记录和旧条目没有变化，新宠物的故事和形象里没有旧宠物的内容，定时任务只有一个 |
| M4 | 领养新宠物前讲清楚并确认 | 已经有宠物时，先讲清两种做法各自的结果：换掉现在这只（旧记录进备份，新宠物接手原来的 Pet 条目和 cloud ID），还是再养一只（新建条目和 cloud ID，原来那只保持原样）。用户确认后才进入[领养前的说明和确认](DEVELOPMENT_PLAN.zh-CN.md#领养前的说明和确认)和领养旅程 | 用户只说「再领养一只」「换一只」「重新开始」时，都先得到这次确认；没有明确回答就不开始 |
| M5 | 多只宠物的数据 | 每只宠物一份独立的记录：自己的 soul、memory、state、故事和素材。另有一处记着上次激活的是哪只 | 两只宠物各完成几篇故事后，互相的记录、素材和 memory 没有混在一起；旧的单只记录读出来就是其中一只 |
| M6 | 多只宠物的同步 | 每只宠物有自己的 Pet 条目和 cloud ID，换形象只换到它自己的那一个。每只宠物有自己的宠物简介 | 给其中一只换形象后，回读两只的云端图：只有这一只变了。在 Dots 里分别选两只，看到的是各自的形象 |
| M7 | 唯一激活的宠物，以用户在 Codex 里选中的为准 | 同一时间只有一只宠物是激活的。开发时先试能否读到用户当前选中的 Pet 对应哪只 GenPet：读得到就以它为激活的宠物，定时故事和用户的斜杠命令都作用在它身上。其他宠物保持原样，再被选中时它知道过了多久 | 选中 A 时跑定时检查和每条斜杠命令，改的都是 A 的记录；改选 B 后同样检查，改的都是 B，A 没有变化；每条命令的结果里写明作用在哪只宠物上；切回 A 后的第一篇故事提到了隔了多久 |

## 最后由用户判断

脚本和逐条检查只能说明规则有没有被遵守。下面三件事要用户看过模拟结果后自己判断：

- 这些内容像不像一只自己养的宠物。
- 和自己有没有联系。
- 看完想不想知道它接下来怎样。
- 它是不是和自己一起长大的：回头看它的 memory，记的是不是两个人一起过的这段时间。

## review 时可以留意的地方

这是汇总时看到的，没有改动用例本身。

有意重复的：S 组在文字模拟里查规则，V 组在真实运行里看结果，所以同一条规则会出现两次。

| 规则 | 文字模拟里 | 真实运行里 |
| --- | --- | --- |
| 画过的形象复用，不重画 | S9 | V3、V4 |
| 特殊形态结束时换回原来的形象 | S8 | V3 |
| 换装和特殊形态的分界 | S13 | V3、V4 |
| 孵化时请用户起名 | S20 | V2 |
| 成长的消息里有新样子的图 | S23 | V2 |
| 到了最晚时间必须成长 | S7 | T5、U1 |
| 敏感内容不使用、不保存 | S3、S12 | A5 |

编号和内容不太对应的：

- S18、S19 说的是领养前的说明，S20 说的是孵化，内容上属于领养和成长，编号却在 S 组。
- M 组在开发计划里的顺序是 M1、M2、M3、M8、M4，M8 是后来插进去的。

可能还缺的：

- 「真的去读用户资料」现在没有单独的用例。A6 只查每条了解有没有来源，查不出这次是否真的读了 Codex 记忆。可以加一条：有 Codex 记忆时，领养和故事的内容用到了其中的资料，并标得出是哪一条。
- 定时检查本身没有用例：电脑开着时是不是每 5 小时触发一次，`/genpet-stop` 之后是不是真的停了（E3 只查停的期间没有检查）。
- 领养旅程一共要用户等多久，没有用例。
