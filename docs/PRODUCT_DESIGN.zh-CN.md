# Codex Pet Design

本项目计划提供 Codex Dots 和 Codex 普通 Pet 两个版本，主要围绕 Codex Dots 版本推进产品设计。本文整理产品构思，包括基因、进化、特殊变化、状态变化、宠物故事和实现方向。领养故事是否有意义、能否让用户感受到联系，是核心设计要求。

运行时的产品规则以 [meta.md](../framework/prompts/meta.md) 为唯一来源；工程问题、0.5.0 实现与待验证事项见 [工程设计与待决问题](ENGINEERING.zh-CN.md)。

## 开源框架目标

插件以可修改的开源框架为目标。宠物一致性的元设计、各项宠物机制及其提示词尽可能模块化，可以分别组织到不同文件中，让后续开发者能够理解、修改和替换相应部分。

插件代码和提示词尽可能轻量，不做过度工程。能够由 Agent 根据运行时上下文自行决定的内容，交给 Agent 决定。模块化服务于理解、修改和替换，具体文件与实现的拆分按实际需要进行。

具体的模块边界、文件组织、输入输出与规则组合方式仍需细化。内容生成保持开放，框架同时需要可靠地管理宠物身份、状态和各宿主的接入。

## Agent 自主判断

用户资料的选择、观察范围、进化触发判断，以及故事和变化的具体内容，由 Codex Agent 在运行时结合所在环境实际可用的上下文与宠物记录决定。插件不预设封闭的资料来源清单、固定观察天数、变化分类或数值触发阈值，也不把这些内容作为必须逐项提前确认的配置。

产品规则说明产品目标与判断依据：领养需要与用户建立有意义的联系，进化依据用户近期有意义的变化（不限于工作），成年后的特殊变化受用户活动影响，各项内容延续同一只宠物的身份与经历。已明确的阶段关系、默认日常时刻、像素风格、开放形象和对话输出范围继续保留。

Agent 每次判断需要参考当前宠物的基因、阶段、已有形象和故事记录。判断与执行结果在内部保存，后续调用据此延续；对话框仍只呈现宠物故事的文本与图像。

工程上按宠物唯一编号定位并更新对应的 Pet／Avatar；目标正在激活使用时，即时刷新其可见形象。独立编号、持久保存、避免重复执行和宿主接入需要可靠实现，具体接口与格式需要实现和验证。

## 产品版本

| 版本 | 当前定位 |
| --- | --- |
| Codex Dots 版本 | 主要设计版本。在 Dots 独立环境中运行，使用其自有 Avatar 自定义机制。 |
| Codex 普通 Pet 版本 | 在 Codex 本地环境中运行，接入普通原生 Pet。 |

两个版本的宠物分开管理，各自拥有独立的编号、状态、故事记录与素材。框架可以复用元设计、宠物机制与提示词的组织方式，宿主接入与安装方式分别实现。

Dots 本身具有主动行为，需要确定宠物机制如何接入这一能力。Dots 端的安装与工程接入，可以考虑由 Dots Agent 在自己的运行环境中完成。

## 命令与对话范围

- 保留斜杠命令，作为用户明确发起操作的入口。
- 原“状态变化”命令改为“新故事”入口，使用 `/genpet-story` 替代 `/genpet-state`。调用的目标是形成一段新的宠物故事，由故事决定当次状态、形象变化以及文本与图像表达。
- 用户通过命令明确要求与宠物对话时，宠物可以给出响应。
- 直接与宠物对话的交互不作为当前强调和设计的主要功能。

这些约束针对 GenPet 提供的功能。Dots 主动能力的接入围绕宠物故事、形象和状态变化展开，具体接入方式仍需验证。

0.5.0 开发版已将 `/genpet-state` 替换为 `/genpet-story`；新命令先形成故事，再决定状态与形象。新故事的任务提示词见 [story.md](../framework/prompts/story.md)。

## 对话框输出

插件每次调用后，对话框中与用户交互的输出限定为宠物故事，由文本与图像配合表达。

对话框不输出插件运行过程说明，包括步骤预告、工具调用解释、执行日志、基因生成说明、安装或更新报告等工程内容。宠物的变化通过故事与图像来呈现，叙述视角、篇幅和图文组织方式由当次内容决定。

这一输出约束适用于 Codex Dots 与普通 Pet，以及初始化和后续各项机制。用户通过命令明确要求与宠物对话时，仍按已有范围提供宠物内容的响应，并遵守同一输出边界。

资料依据、基因描述、状态记录与执行结果属于内部生成和保存所需的信息，不能直接作为面向用户的回复。故事须与实际完成的变化和可用素材相符，不能把尚未完成的形象更新或变化写成已经发生。

对应的运行提示词见 [output.md](../framework/prompts/output.md)。

## 基因机制与宠物形象

### 初始化与蛋的获取

Pet 初始化时，结合用户资料和“随机探险”机制获得一颗蛋。这颗蛋决定宠物后续的形象与进化。

获取蛋与形成基因之间的关系如下：

1. 根据用户数据，建立对用户的了解。
2. 生成一段如何获得这颗蛋的用户故事，说明蛋是在什么地方、如何获得的。
3. 用户故事决定获取蛋的地点，并为宠物设计提供依据；根据领养经历与地点选择人类熟悉的灵感来源，再生成宠物基因。
4. 宠物基因决定后续各个进化阶段的形象。

每次基因生成是元设计约束下的一次宠物设计。Agent 自行选择与用户相关的资料，形成有意义的领养故事及地点，再由这段经历选择人类熟悉的自然形象、文化形象或 IP 等作为灵感。需要说明借鉴什么、为什么由本次相遇选择它，以及它如何转化为主体形态和主要特征；插件不预设地点菜单、灵感清单或地点到形象的固定映射。

随机性探索这些依据允许的不同诠释。熟悉来源应参与身体构成，让用户能够理解这只宠物为什么为自己这样设计；不能先拼一个罕见身体，再补一个灵感名称或通用故事。概念可以作为主题，但抽象词或虚构地点名本身不能代替可辨的形象来源。人类熟悉也不代表已知用户喜欢，不补造用户偏好或既有来源的设定。

领养故事必须有意义，能够与用户建立联系。这是初始化的核心要求，需同时考虑故事内容和最终生成的宠物形象：用户为何遇到这颗蛋、这段获得经历为何与用户相关，以及随机形成的宠物为何让用户感到有所关联。

这里的蛋是字面意义上的蛋：完整的常规卵形蛋壳。不同宠物的整体蛋形相近，差异主要体现于壳面色彩、纹理和斑纹。初始化时已经形成基因，蛋壳只透露部分线索，孵化后才显现各自不同的身体构成。不能把“核心形象差异超出颜色”的要求应用为不同的蛋必须有不同构造。

### 宠物形象规范

宠物采用适合小尺寸 Avatar 的卡通像素风格：轮廓紧凑，身体简化而适度夸张，靠少量清楚的像素色块表达。灵感来源转化为角色设计，不照搬现实比例、写实羽毛或解剖材质；写实插画带像素边缘不满足这一要求。孵化后仍有可辨的生物身体与器官，通过简洁造型建立生命感。

幼年体需要一眼显出尚未长开的身体。来源的成年长颈、修长肢体或完整展开结构可留到后续进化逐渐显现；幼年保留少量尚未发育的身份线索，不能只把成年来源缩小。具体幼态由每只宠物决定，不统一规定所有宠物的大头比例或身体模板。折纸鹤灵感可以保留，而幼年形象不应直接成为细长、写实的成熟小鹤。

灵感来源保持开放，但必须是人类熟悉的可辨形象，并有领养故事中的选择依据。来自物体或文化意象时，通过拟生物或拟人方式形成生命角色。此前的来源示例不构成分类表、可选菜单或必须覆盖的类别。参考 MapleStory 怪物将不同来源塑造为有器官的生命角色的思路，仍采用 Codex 像素风，不规定既有怪物类别或共同头身。

宠物可以有五官，也可以没有五官。无脸宠物仍需通过可辨的生物身体、器官和姿态建立生命感；不统一规定眼睛、嘴或肢体组合。身份连续性与状态表达依据这只宠物自身的身体特征，生成时不擅自改变已经形成的五官设定。

避免所有宠物只是同一底稿的换色，主体设计应体现各自的故事与灵感依据。不要求每对宠物必须具有不同身体，也不以差异大或新奇作为成功标准；相同故事可以支持相近的设计。同一只宠物则通过自己的基因延续身体与器官关系，在不同阶段表现出可理解的进化。共同蛋形、像素风、生物特征和有依据的设计是框架边界，具体构成与识别特征由每只宠物分别形成。

### 完全替换旧生成方案

旧生成方案的范围受限，形象差异过小，用户明确要求将其完全改掉。0.5.0 已移除固定宠物家族和少量形态参数组合的生成基础，使用开放的宠物描述与产品规则。

重构前生成方案的限制包括：

- 基因主要记录色相及三种纹理；形态在孵化时才形成，并限定为同一个 `roundling` 家族、三种身体形状和三种附肢。
- 图像提示词进一步统一了宽椭圆头、方形眼睛、小嘴、两只手和两只脚等身体构成。此次移除这些固定身体组合，保留字面蛋及共同蛋形的产品设定。

需要替换的是生成机制和提示词共同施加的限制，不能通过增加配色或扩大旧形态枚举来完成这次调整。

已明确的新方向为：

1. 初始化时根据有意义的领养经历与获取地点选择熟悉灵感，形成设计依据与基因，基因从蛋开始作为后续形象与进化的依据。
2. 产品规则规定有依据的设计、字面蛋、孵化后的生物特征、用户关联、开放来源、连续性与像素风格；具体形象由运行时生成。
3. 每只宠物形成自己的生物身体、器官关系和识别特征，后续一致性作用于该宠物自身。所有宠物不共用一套身体模板。
4. 基因和图像提示词都传递灵感来源、故事选择理由及主要身体转化关系。工程格式、动画和宿主接入的要求分别处理，避免将输出格式要求扩大为统一的角色造型。

0.5.0 的实际可修改提示词位于 [framework/prompts](../framework/prompts/meta.md)，已接入运行程序。早期草案已冻结归档于 [design-drafts](archive/design-drafts/initialization-meta-design.zh-CN.md)，仅保留设计依据。

## 进化机制

宠物按照基因形成各个阶段的形象，阶段关系为：

**蛋 → 幼年体 → 青年体 → 成年体**

是否进化，根据用户近期是否出现有意义的变化来决定，变化可以来自工作、学习、兴趣、经历或环境，不再按照固定几天进入下一阶段。

基因负责各阶段形象的连续性，Agent 根据实际可用的用户资料与该宠物的阶段和历史，选择参考范围、理解用户近期的变化，并判断是否进入后续阶段。具体触发条件由 Agent 当次判断，不预先规定固定观察天数、变化类别或数值阈值。

判断及其依据作为内部记录延续，避免后续调用脱离该宠物已有的阶段与经历。对用户呈现的是进化对应的故事与图像。

## 特殊变化机制

进入成年体后，宠物会产生特殊变化。特殊变化根据用户一段时间内的活动情况，以随机方式产生，并配有与用户产生联系的宠物故事。

活动的参考范围、随机变化的内容、影响范围与持续方式由 Agent 根据当时的用户活动、宠物基因和已有经历决定，并延续这只宠物的身份。插件不预设特殊变化的类型清单。

## 新故事与状态形象变化

新故事是当次状态和形象变化的依据。Agent 结合用户资料与宠物已有经历，先形成新的宠物故事，再根据故事决定宠物的状态、形象变化及故事的文本与图像表达。具体变化保持开放，换装是已提出的例子。

“新故事”命令、日常定时触发和 Dots 主动行为使用这一内容逻辑。默认日常时刻为：

| 时段 | 时刻 |
| --- | --- |
| 早上 | 07:00 |
| 中午 | 12:00 |
| 下午 | 16:00 |
| 晚上 | 21:00 |

这些时刻触发新的宠物故事，并由故事决定当次状态与形象变化。各时刻不预先绑定固定故事、状态或装扮。

### 状态形象的保存与复用

已经生成的状态形象保存在对应宠物的记录中，与该宠物的唯一编号及相关故事和状态上下文关联。后续新故事需要某种状态形象时，由 Agent 判断已有素材是否适合当前基因、阶段与故事；适合时直接复用，需要新的表达时再生成并保存。

保存与复用保持轻量，不预设固定状态分类、服装目录或故事到素材的映射。复用的素材继续用于同一编号对应的目标 Pet／Avatar，目标激活使用时按既定规则即时刷新。

## 宠物故事

### 故事与用户的关系

宠物故事与用户相关联，同时呈现宠物拥有自己生活的感觉。故事既要与用户产生联系，也要表现宠物自身的经历与生活。

故事贯穿以下事件：

| 事件 | 故事内容 |
| --- | --- |
| 领养蛋与初始化 | 告诉用户如何获得这颗蛋，以及获取地点。 |
| 进化 | 围绕进化产生与用户相关联的宠物故事。 |
| 特殊变化 | 围绕特殊变化产生与用户相关联的宠物故事。 |
| 新故事与日常变化 | 形成与用户相关的宠物新经历，由故事决定状态、形象变化及图文表达。 |

### 文本与图像的表达

宠物故事结合文本与生成图片来表达，文本和图像相互配合。图片可以是场景图，也可以是 artifact。

以下是已提出的表达示例，后续形式由故事内容和表达需要决定：

- 表现宠物经历的场景图。
- 宠物出去玩后带回的明信片。
- 宠物拍摄的一张照片。
- 宠物展示自己今天的 OOTD，也就是当日穿搭。
- 宠物自己的时间表安排。

这些示例帮助说明宠物拥有自己生活的感觉。故事内容、状态变化和表达形式保持开放，由 Agent 根据当次内容选择，文本与图像共同表达当次经历及其与用户的联系。素材制作与宿主呈现需要工程接入。

## 实现方向

当前提出的实现方向包括：

- 普通 Pet 版本按唯一编号更新对应原生 Pet，目标激活时利用该宿主的刷新机制即时呈现形象。
- Dots 版本按唯一编号更新对应 Avatar，目标激活时利用 Dots 自有机制即时呈现，并接入已有主动行为；安装与环境相关工程可以考虑由 Dots Agent 自行实现。
- 利用自身的 Image Gen 和其他工具调用，生成新的宠物形象，或将宠物故事视觉化。
- 利用定时任务进行周期性检查并触发新故事，由故事决定宠物状态和形象变化。
- 将元设计、宠物机制、提示词及宿主接入尽可能模块化，支持开发者修改和替换。

本节记录产品方向。0.5.0 的实现情况与未决事项见 [工程设计与待决问题](ENGINEERING.zh-CN.md)。

两个版本分别管理宠物身份与记录，可复用框架中的设计定义、机制与提示词组织方式。Dots 已有的主动能力、定时任务与命令调用需要共同服务于上述设计，并遵循直接对话的功能范围。
