# 0.5.0 本地开发版验证

本轮交付两个独立包：`plugins/genpet-dots` 和 `plugins/genpet`。共享产品规则、任务提示词和接入说明在 `framework`，运行包有自己的副本。0.5.0 供用户跨设备验证；真实用户环境未在开发中升级、领养或修改。

## 用户验证入口

Dots 为主要验证环境。将本次 `plugins/genpet-dots` 包或开发归档放到 Dots 可用的持久位置，让 Dots Agent 阅读包内 `skills/genpet-start/SKILL.md`、`references/workflow.md` 与 `references/dots.md`，按自己实际提供的 Avatar 能力安装并绑定目标。包内运行时自包含，需要 Node 22+。它不使用普通 Pet 的本地 IPC，也不读取桌面宠物记录。

可以交给 Dots Agent 的请求：

> 请使用本次提供的 GenPet Dots 0.5.0 包开始我的宠物。先阅读这个包的 genpet-start、共享 workflow 和 Dots 接入说明；在你的独立环境中保存唯一编号并绑定你实际使用的 Avatar。使用你自己的 Avatar 自定义和刷新机制，需要时实现包内说明的轻量接入。先形成有意义的领养故事，再由这段经历选择人类熟悉的形象灵感，保存设计依据与基因，生成字面意义上的蛋，并按 Asia/Taipei 的 07:00、12:00、16:00、21:00 设置故事任务。与我的对话只呈现宠物故事文本和真实图像。

普通 Pet 的本地验证可以在新的验证 chat 中明确要求读取本仓库 `plugins/genpet/skills/genpet-start/SKILL.md` 并使用该目录下的 0.5.0 运行时。避免误用已安装的旧版技能。发现旧记录时先按 storage 说明迁移，保留原来的宠物；验证全新基因初始化时，另明确请求 `/genpet-reset`。本说明不会替用户执行这些操作。

## 需要用户判断的结果

检查领养故事是否有意义、熟悉灵感为什么由这段相遇选择，以及主体形态是否体现这些依据，让你能理解它为什么为自己这样设计。内部设计说明可通过保存的步骤检查，不作为插件故事回复。单独检查小尺寸 Avatar 的卡通像素表达，以及幼年是否一眼尚未长开；可辨来源、像素边缘或缩小成熟身体都不能代替这两项。再检查字面蛋、生物身体、无脸宠物与后续身份连续性。蛋形相近、壳色纹理不同符合设定；身体不同不能单独证明设计成功。新故事应先决定状态，已保存形象能合理复用，输出只有故事与图像。

在对应宿主核对实际 Avatar ID。目标激活时应即时显示新形象，目标未激活时保持当前选择。请求已交付和看到新形象是两回事。

## 本轮工程检查

类型检查和 59 项工程单元测试通过，包括 genes 必需保存非空 designBasis 的格式检查，两个插件包使用一致的 0.5.0 版本。生成单元验证使用虚构上下文，不作为真实领养故事。各轮结论与状态见 [生成测试记录摘要](evidence/README.md)，原始报告与图像只保存在本地 `output/`。

当前轮 [故事依据静态复测](evidence/README.md#故事依据静态复测)：用户接受 A 蛋 v1 与 B 幼年 v2，分别作为字面蛋与卡通像素幼态的正例；B v1 过于写实、C v1 不可爱，均已撤回。相关规则已写入 `framework/prompts/meta.md`，下一轮按运行时路径重测。

紧邻上一轮的 [生物边界复测](evidence/README.md#生物边界复测) 因新增设计依据原则中止，局部检查保留，但不作为当前接受。更早的 [首轮实际形象生成](evidence/README.md#首轮实际形象生成)、[静态形象单元](evidence/README.md#静态形象单元) 和 [故事生成单元](evidence/README.md#故事生成单元) 的图像结论，是在把蛋当作非蛋构造、把开放来源扩展为非生物形象的错误边界下得出的，已撤回，图像只作负例。

当前产品规则、基因、初始化、形象和图像检查模块要求有依据的设计：由领养故事选择熟悉来源，生成前记录主要形态的转化理由，实图检查其可见表达；不以新奇或不同身体为目标。字面蛋与孵化后的生物边界保留。无脸仍允许，蛋图只用于壳面线索。新增开放的 designBasis 单元结果，仍保存在既有内部步骤中，依据同时留在基因文本；未新增物种分类、器官菜单或顶层 Pet 存储结构。历史样本与快照保留，图片失败继续沿用同一份有效基因和计划修正。

## 结构化单元入口

当前提示词进一步拆成 context、encounter、genes、story、evolution、appearance、image-review、output 八个单元，各有固定输入名、开放结果和检查点。编排与格式见 [单元说明](../framework/references/generation-units.md)；虚构资料与在 Codex 中运行的核心模块测试见 `tests/agent/README.zh-CN.md`。

例如在本地只测试基因单元：

```text
node plugins/genpet/dist/cli.js unit-request genes ABSOLUTE_GENES_FIXTURE
node plugins/genpet/dist/cli.js verify-unit genes ABSOLUTE_GENERATED_RESULT
```

把第一条返回的精确请求交给测试 Agent，并保存其结果。第二条只核对字段与基本类型，不自动证明宠物之间的差异。正常运行使用 `record-step OPERATION_ID UNIT RESULT_FILE` 保存简短内部产物，完成故事后保留这些步骤，对用户仍只输出故事与图像。

新增工程检查覆盖固定输入格式、重复步骤去重、修订保留、步骤不改计划或阶段、完成故事保留产物，以及测试命令不创建宠物记录。

结构化生成的实际检查见 [结构化文本单元](evidence/README.md#结构化文本单元)（当前）和 [结构化视觉单元](evidence/README.md#结构化视觉单元)（格式与追溯当前，图像结论撤回）。

源代码的字段格式测试与实际生成语义检查分别报告；样本不代表统计成功率，也不替代用户对意义、形象与宿主显示的验证。

基础宠物形象测试使用真实生成与实际查看；附带动画在 0.5.0 未重新生成。最新提示词与格式修正后的类型检查和全部 59 项工程单元测试通过，两个包已重建。2026-10-02 跨设备交付前，完整 `npm run verify:release` 通过：与已抓取的 `origin/main` 比较版本 0.4.0 → 0.5.0，在临时 `CODEX_HOME` 中通过官方 CLI 安装两个包，分别核对 68 与 34 个文件，并完成隔离 CLI 和可选调试器检查。普通 Pet 的测试脚本在关闭宿主通讯时明确记录合成的未激活目标，不将未知激活状态视为完成，也不宣称看到真实显示。

真实宿主端到端验证由用户后续进行。各宿主接入的未决事项见 [工程设计与待决问题](ENGINEERING.zh-CN.md#待决问题状态)。开发检查没有安装到用户环境或操作真实 Pet、Avatar、调度。
