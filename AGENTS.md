# GenPet release rules

- Every published plugin upgrade must increment the semantic version, including changes only to skills, prompts, bundled documentation or scripts. Use a patch bump for compatible fixes; choose minor/major for broader or breaking changes. Do not bump merely for each local edit.
- Keep package.json, package-lock.json (root and packages[""]), plugins/genpet/.codex-plugin/plugin.json and the generated plugins/genpet/package.json consistent. Rebuild the generated runtime after changes.
- Before publishing, run npm run verify:release. The version gate compares the deliverable against origin/main (or GENPET_RELEASE_BASE when explicitly set); fetch the release base before release checks. Never bypass a failed gate by only changing the comparison base.
- When installing from an existing marketplace, refresh it even if the plugin is currently uninstalled. `marketplace add` returning already-added does not establish freshness.
- Verify installed manifest versions and file hashes against the refreshed marketplace source using scripts/verify-install.mjs. Report the marketplace commit, installed version and installed path. Directory names and installed/enabled status alone are insufficient.
- Do not reset, adopt, age or regenerate a user's Pet as part of installation verification. Use an isolated CODEX_HOME for release tests. New chats load updated skills and tools; do not promise an active chat has discarded its old instructions.

# GenPet framework design rules

- Keep plugin code and prompts as lightweight as possible. Avoid over-engineering; add abstractions, configuration and modules only when needed for a concrete requirement.
- Let Codex Agent make decisions at runtime whenever it can do so from available context and Pet records. This includes selecting relevant user information (not only work), observation ranges and evolution triggers. Do not turn these judgments into exhaustive presets, fixed thresholds or mandatory upfront configuration.
- Use prompts to convey product goals, meta-rules and judgment guidance while leaving generated content and forms open. Keep prompts and mechanisms easy for developers to understand, edit and replace; split files according to practical needs.
- Structure generation prompts into independently testable units with explicit inputs, observable intermediate results and review points. Save brief results and source references internally; keep creative content and Agent judgments open. Do not treat a valid JSON contract or a model's own pass claim as proof of semantic or visual correctness.
- Treat every new genome as a Pet design under the meta-rules. Choose recognizable inspiration from human-familiar natural or cultural forms, including IP, because of the adoption story and its meaningful user connection. Save a concise design basis explaining the source, story link and how it informs the main physical traits. Randomness explores grounded interpretations; novelty or difference alone is not a design reason. Keep sources open rather than prescribing a catalog, and do not invent the user's preferences or an existing source's lore.
- Eggs are literal eggs: a complete conventional egg shell with a similar overall egg shape across individuals. Individual clues primarily vary shell colors, textures and patterns. Core body diversity is expressed after hatching, not by replacing the egg with an object or abstract structure.
- Hatched Pets must be recognizable fantasy living creatures with visible biological bodies and organs. Sources may remain open, including objects and concepts, but must be transformed into anthropomorphic or creature-like Pet designs. A complete face is optional; biological character is required. Do not enforce a shared body, face, organ menu or species taxonomy.
- Design cute, approachable cartoon pixel Avatars readable at small display sizes: compact silhouettes, simplified and appropriately exaggerated forms, few clear color blocks. Familiar inspiration is transformed rather than copied with realistic proportions or anatomical texture. Hatchlings must visibly look undeveloped; mature source features can develop in later stages. Neither a realistic illustration with pixel edges nor a scaled-down adult passes. Do not impose a universal head/body ratio.
- Visual review checks the product boundary before identity, diversity or story details: an egg reads as an egg, and a hatched Pet reads as a cute living companion without its name or story. Preserve out-of-bound candidates as negative examples rather than product acceptance evidence.
- The former state-change command becomes a new-story entry point. Form the new Pet story first, then let it determine state and appearance changes and the story's text-and-image expression. Save state artwork under the Pet's identity and let the Agent reuse suitable existing artwork when a later story calls for it.
- Use code for necessary engineering support, including identity, persistence, host binding and reliable updates. Preserve explicitly agreed product behavior: update the target Pet/Avatar by its unique ID, and refresh its visible appearance immediately when the target is active.
