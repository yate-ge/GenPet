# GenPet release rules

- Every published plugin upgrade must increment the semantic version, including changes only to skills, prompts, bundled documentation or scripts. Use a patch bump for compatible fixes; choose minor/major for broader or breaking changes. Do not bump merely for each local edit.
- Keep package.json, package-lock.json (root and packages[""]), plugins/genpet/.codex-plugin/plugin.json and the generated plugins/genpet/package.json consistent. Rebuild the generated runtime after changes.
- Before publishing a new version, check compatibility with the currently published version so that updating cannot lose user data or break working functions. Review what the change removes or renames (record fields, stored files, CLI commands, skills, host bindings, schedules) and load representative existing data, including records written by earlier versions, with the new build in an isolated CODEX_HOME and data directory. Existing Pets, stories, artwork, bindings and schedules must still load and work; a format change needs a migration that preserves the original. Report what was checked. Do not publish while a compatibility risk remains unresolved.
- Never push to the remote on your own. Prepare the change, run the checks, report what changed, and push only after the user has reviewed and explicitly confirmed it. Approval to push earlier changes does not cover later ones.
- Before publishing, run npm run verify:release. The version gate compares the deliverable against origin/main (or GENPET_RELEASE_BASE when explicitly set); fetch the release base before release checks. Never bypass a failed gate by only changing the comparison base.
- When installing from an existing marketplace, refresh it even if the plugin is currently uninstalled. `marketplace add` returning already-added does not establish freshness.
- Verify installed manifest versions and file hashes against the refreshed marketplace source using scripts/verify-install.mjs. Report the marketplace commit, installed version and installed path. Directory names and installed/enabled status alone are insufficient.
- Do not reset, adopt, age or regenerate a user's Pet as part of installation verification. Use an isolated CODEX_HOME for release tests. New chats load updated skills and tools; do not promise an active chat has discarded its old instructions.
- For "log and git push" in this project, keep the log in this repository. Do not read or modify Obsidian or its Daily Note unless the user explicitly includes that vault in the task.

# GenPet repository layout

- `plugins/genpet/` is the only copy of the plugin. Edit its skills, debugger page, manifest, host config and README in place. `npm run build:plugin` generates only `plugins/genpet/dist/` and `plugins/genpet/package.json`; never edit those by hand. Do not recreate `framework/` or top-level `prompts/` or `references/` copies.
- Everything the Agent reads at runtime lives in `plugins/genpet/skills/genpet/`, organized by owner: `rules.md` is the only source of product rules; `output.md` governs what the user sees; `context/` holds how user context is read (README) and the context unit; `designers/<Role>/` holds the role's README and the unit prompts it owns; `flows/` holds end-to-end procedures (README for shared conventions, adoption, stories with image coordination, naming, scheduling); `host/` holds host formats and capabilities, storage and the unit contracts (`units.json` records each unit's file, inputs and results).
- Write each rule once, in the file that owns it, and point to its section elsewhere (for example `../../rules.md「成长节奏」`) instead of restating it. A role README says only when the role runs, which units it uses in what order and where results go; a unit says what it produces, its own judgment guidance and its checkpoints.
- A new unit goes into its owning role's folder with an entry, including `file`, in `host/units.json`. A new slash command is a thin `plugins/genpet/skills/<command>/SKILL.md` that links into `skills/genpet/`.
- Development and test procedures, test cases and evidence handling belong in `tests/agent/` and `docs/`, never in runtime files.
- When moving or renaming a runtime file, update every link to it and check that all relative links in `plugins/genpet/skills/` resolve.
- `docs/` holds only current documents. Move an outdated one to `docs/archive/<version>/`, fix its relative links and every link to it, and list it in the archive section of `docs/README.md`.

# GenPet framework design rules

- GenPet must not invoke or depend on Computer Use for Pet selection, visibility, appearance updates or verification. Use the existing host APIs, app-tools, IPC and plugin runtime. Keep display confirmation unknown when the available interfaces cannot verify it; do not substitute a refresh request or selection readback for proof of the displayed image.
- Before desktop appearance updates, check the host's local-to-cloud migration mapping when available. A mapped `custom:` entry and `pet_` ID represent the same Pet; update its actual cloud ID and refresh the cloud Pet resources while preserving selection. Writing only the local atlas or selecting the legacy `custom:` ID does not update a migrated cloud Pet. Verify stored artwork against the accepted image after the update.

- Keep plugin code and prompts as lightweight as possible. Avoid over-engineering; add abstractions, configuration and modules only when needed for a concrete requirement. This is both a design rule and a coding rule: when the Agent can handle a situation from context, do not write code, fixed rules or an extra flow to constrain it. For example, when the user declines the adoption notice, the Agent stops and says so.
- Let Codex Agent make decisions at runtime whenever it can do so from available context and Pet records. This includes selecting relevant user information (not only work), observation ranges and evolution triggers. Each story observes the user's current situation from recent sessions, reading only as far as the judgment needs and never saving raw session content; Codex memories describe who the user is and serve adoption and growth. Do not turn these judgments into exhaustive presets, fixed thresholds or mandatory upfront configuration. Exception agreed for growth: fixed pace ceilings (egg 5 hours, hatchling and juvenile one week each) are only latest-time fallbacks that guarantee change; an adult transformation (幻化, stored as the special form) is never forced in, lasts at most two days and comes at least a week after the last one; before them growth follows accumulated experiences: each rewrite of the Pet's memory counts as one experience, and after five in a stage the Agent picks the story that advances it, preferring one that coincides with a real change in the user's life. Growth is never shown to the user as a number. Exception agreed for story variety: text-only stories may run at most twice in a row, and a text-only story must correspond to a user-related context item; before that fallback the Agent decides each story directly from the observed user situation and varies it from recent content. Stories are not drawn from seeded candidates; a seeded choice is kept only for the genes design at adoption, where independent adoptions have no shared history to vary against. Words the user left in /genpet-chat get a response in the next story, in the Pet's own way.
- Use prompts to convey product goals, meta-rules and judgment guidance while leaving generated content and forms open. Keep prompts and mechanisms easy for developers to understand, edit and replace; split files according to practical needs.
- Structure generation prompts into independently testable units with explicit inputs, observable intermediate results and review points. Save brief results and source references internally; keep creative content and Agent judgments open. Do not treat a valid JSON contract or a model's own pass claim as proof of semantic or visual correctness.
- Treat every new genome as a Pet design under the meta-rules. Choose recognizable inspiration from human-familiar natural or cultural forms, including IP, because of the adoption story and its meaningful user connection. Save a concise design basis explaining the source, story link and how it informs the main physical traits. Name the inspiration specifically: a particular species or breed, a particular legend, or a particular character from a named work. Then design its attributes, abilities and distinctive organs or structures in detail, each with a reason. A generic animal with one added part or a recolor is not a design. Randomness explores grounded interpretations; novelty or difference alone is not a design reason. Keep sources open rather than prescribing a catalog, and do not invent the user's preferences or an existing source's lore.
- Eggs are literal eggs: a complete conventional egg shell with a similar overall egg shape across individuals. Individual clues primarily vary shell colors, textures and patterns. Core body diversity is expressed after hatching, not by replacing the egg with an object or abstract structure.
- Hatched Pets must read at a glance as cute living companions. They need not resemble animals. A tool weights the source type in the background: most Pets come from natural animals and plants, some from everyday objects turned into characters, and a few from legends, myths, named works or other imagined beings. This weighting is an agreed fixed mechanism and is never shown to the user. Every hatched Pet has facial features, at least eyes. Do not enforce a shared body, organ menu or species taxonomy.
- Cuteness comes first. No design may be unsettling or unpleasant to look at, and a Pet drawn from an ordinary animal or plant must still be interesting and cute.
- Design cute, approachable cartoon pixel Avatars readable at small display sizes: compact silhouettes, simplified and appropriately exaggerated forms, few clear color blocks. Familiar inspiration is transformed rather than copied with realistic proportions or anatomical texture. Hatchlings must visibly look undeveloped; mature source features can develop in later stages. Neither a realistic illustration with pixel edges nor a scaled-down adult passes. Do not impose a universal head/body ratio.
- Visual review checks the product boundary before identity, diversity or story details: an egg reads as an egg, and a hatched Pet reads as a cute living companion without its name or story. Preserve out-of-bound candidates as negative examples rather than product acceptance evidence.
- A Pet is the companion the user found on an adventure, living in a virtual world linked to the user through the host, the user's readable context and their interactions. A story is the Pet's response to observing the user's current situation, shaped by its personality and their relationship. Express the connection through what the Pet does, wears, makes or gives and through its home, as everyday actions readable at a glance; the Pet may speak to the user directly, but do not narrate the user's facts, write "you did X, so it did Y" bridges, or rely on symbols that need earlier episodes. Everything the Pet does or gives happens in its own virtual world: it may do something alongside the user in its home or give a virtual item, but it never pretends to have acted in the user's real world (washed their brushes, laid out their pans); it may respond to what it can read in the user's sessions. Respond to ordinary situations at an ordinary scale. What it says has a concrete point of its own feeling, gently, without judging or arguing with the user's views. No story for its own sake: the main line is life as the user's new Pet, with the adoption journey only an occasional memory. When the user is busy, favor companionship and visible state changes; after a long absence, favor travel and home upkeep told through objects, appearance and home.
- A Pet changes in three ways. Everyday changes (日常) keep the body: what it wears, holds or does, its momentary condition (sleepy, focused, a little unwell) and a bit of surroundings; its condition belongs to its own world and never mirrors the user's health or mood. Growth develops the body stage by stage. A transformation (幻化) is a rare, supernatural, temporary change for adults only: when the user has kept the same state for three days or more, the Agent may pick a transformation object and blend it with the Pet's identity core so the look changes greatly yet is still recognizably this Pet. It is the Pet's own playful response, never a judgment of the user, never caused by late nights, overwork, mood or health, and stays cute and safe. /genpet-grow confirms first, transforms an adult and ends a current transformation.
- Each host animation row is a trigger slot, not a literal action. PetDesigner designs every slot's continuous frames for the current look and condition: a resting Pet does not get up and run, while direction and click slots still read clearly. Review checks the slot's response, not literal walking or jumping.
- The former state-change command becomes a new-story entry point. Form the new Pet story first, then let it determine state and appearance changes and the story's text-and-image expression. Save state artwork under the Pet's identity and let the Agent reuse suitable existing artwork when a later story calls for it.
- Use code for necessary engineering support, including identity, persistence, host binding and reliable updates. Preserve explicitly agreed product behavior: update the target Pet/Avatar by its unique ID, and refresh its visible appearance immediately when the target is active.
- Keep every artifact and all test data produced during development and testing (reports, stories, images, raw units, snapshots, run output); do not delete them. They are never committed to git and go directly to the user's Google Drive. Only the summary index `docs/evidence/README.md` is tracked. Keep the repository small: it is cloned in full by the marketplace under a fixed 30-second timeout, so do not commit generated images, PDFs or run output.
