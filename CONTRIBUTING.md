# Contributing to GenPet

Thanks for helping. Read [the design document](docs/DESIGN.md) first: it explains the design idea, the principles every change follows and how the pieces fit. The product rules the plugin runs on are in [plugins/genpet/skills/genpet/rules.md](plugins/genpet/skills/genpet/rules.md).

## Setup

Use Node 22 or later.

```bash
npm ci
npm run verify:fast
```

`verify:fast` runs type checks, formatting and the unit tests. Run the checks that fit your change; do not add tests that only mirror wording or implementation.

## Where to edit

- `plugins/genpet/` is the only copy of the plugin: skills, debugger page, manifest, host config and README. Edit them in place. `src/` is the runtime source. `plugins/genpet/dist/` and `plugins/genpet/package.json` are generated by `npm run build:plugin`; do not edit them by hand. Do not recreate `framework/` or top-level `prompts/` or `references/` copies.
- Everything the Agent reads at runtime lives in `plugins/genpet/skills/genpet/`, organized by owner: `rules.md` is the only source of product rules; `output.md` governs what the user sees; `context/` holds how user context is read (README) and the context unit; `designers/<Role>/` holds the role's README and the unit prompts it owns; `flows/` holds end-to-end procedures (README for shared conventions, adoption, stories with image coordination, naming, scheduling); `host/` holds host formats and capabilities, storage and the unit contracts.
- Write each rule once, in the file that owns it, and point to its section elsewhere (for example `../../rules.md「成长节奏」`) instead of restating it. A role README says only when the role runs, which units it uses in what order and where results go; a unit says what it produces, its own judgment guidance and its checkpoints.
- A new unit goes into its owning role's folder with an entry, including `file`, in `host/units.json`. When a unit's inputs or results change, change its prompt and `host/units.json` together. A new slash command is a thin `plugins/genpet/skills/<command>/SKILL.md` that links into `skills/genpet/`.
- When moving or renaming a runtime file, update every link to it and check that all relative links in `plugins/genpet/skills/` resolve.
- Keep code and prompts small. The Agent chooses sources, context range, design, relationship and story content; code handles identity, persistence, host binding and the few agreed fixed mechanisms listed in [the design principles](docs/DESIGN.md#engineering). Do not add activity taxonomies, personality presets, face templates or configuration for judgments the Agent can make.
- The repository documents are the README, this guide and [the design document](docs/DESIGN.md). Update them when the design changes; delete what is outdated (git history keeps it) and fix every link to it. Plans, discussions and run records do not go in the repository.

## Records and hosts

- Records are version 3, one per Pet ID, with `soul`, `memory` and `state`. Keep immutable identity, existing source history and cloud IDs. Old saved field names stay readable.
- A story keeps the Pet ID resolved when it started.
- Host display, readback, refresh and selection are separate facts; a selection or refresh request does not prove what is displayed. No Pet path depends on Computer Use.
- Before a desktop appearance update, check the host's local-to-cloud mapping when available. A mapped `custom:` entry and its `pet_` ID are the same Pet: update the actual cloud ID and refresh the cloud Pet resources while keeping the selection, then verify the stored artwork against the accepted image.
- Dots uses the same cloud Pet, accepted atlas and record brief through the host's own tools. There is one `genpet` package and one marketplace entry.

## Testing with a real Agent

Content and image checks follow the unit contracts in [host/units.md](plugins/genpet/skills/genpet/host/units.md) and the Agent acceptance suite: the cases are in [tests/agent/CASES.zh-CN.md](tests/agent/CASES.zh-CN.md) and the procedure in [tests/agent/README.zh-CN.md](tests/agent/README.zh-CN.md). Test procedures and cases belong in `tests/agent/`, never in runtime files.

- A valid JSON result or a model's own pass claim is not semantic evidence. Keep the actual upstream results, look at the generated pixels and get an independent review. Keep out-of-bound candidates as negative examples.
- Use an isolated `CODEX_HOME` and a dedicated test Pet. Tests and upgrades must not adopt, age, reset or regenerate anyone's real Pet. Isolated tests cannot prove live display.
- Write test output under `output/`, which git ignores. Do not commit images, PDFs, logs or run output.

## Pull requests

Describe what changed and why, list the checks you ran and their results, and say what you could not verify. Releases are made by the maintainer, as described below.

Report security problems as described in [SECURITY.md](SECURITY.md), not in a public issue.

## Releasing

GenPet is published through the Codex plugin marketplace in [`.agents/plugins/marketplace.json`](.agents/plugins/marketplace.json). The marketplace clones this repository in full under a fixed 30-second timeout, so the repository stays small: no generated images, PDFs, logs or test output in git.

### Versions

- Every published plugin upgrade increments the semantic version, including changes only to skills, prompts, bundled documentation or scripts. Use a patch bump for compatible fixes and a minor or major bump for broader or breaking changes. Do not bump for each local edit; publish one version after the planned change is implemented and verified.
- Keep the version the same in `package.json`, both places in `package-lock.json` (root and `packages[""]`), `plugins/genpet/.codex-plugin/plugin.json` and the generated `plugins/genpet/package.json`.
- Rebuild the generated runtime with `npm run build:plugin` after source changes. Check that removed skills and prompts do not survive in the generated package.

### Compatibility with the published version

Updating must not lose user data or break working functions.

1. Review what the change removes or renames: record fields, stored files, CLI commands, skills, host bindings and schedules.
2. Load representative existing data, including records written by earlier versions, with the new build in an isolated `CODEX_HOME` and data directory.
3. Existing Pets, stories, artwork, bindings and schedules must still load and work. A format change needs a migration that preserves the original.
4. Report what was checked. Do not publish while a compatibility risk remains unresolved.

### Release gate

1. Fetch the release base: `origin/main`, or `GENPET_RELEASE_BASE` when it is set explicitly.
2. Run `npm run verify:release`. It builds the deliverable, compares its version against the release base and validates it in an isolated home.
3. Never pass a failed gate by only changing the comparison base.

### Install verification

- When installing from an existing marketplace, refresh it even if the plugin is currently uninstalled. `marketplace add` returning already-added does not mean the source is fresh.
- Verify the installed manifest version and file hashes against the refreshed marketplace source with `scripts/verify-install.mjs`. Report the marketplace commit, installed version and installed path. Directory names and installed or enabled status alone are not enough.
- Do not reset, adopt, age or regenerate a real Pet during installation verification; release tests use an isolated `CODEX_HOME`.
- New chats load updated skills and tools. An active chat may still follow the instructions it loaded earlier.
