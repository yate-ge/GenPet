# Development and release workflow

GenPet keeps the complete reproducible project on the default `main` branch: runtime source, tests, generation tools, documentation, and publishable example fixtures. The repository root is the Codex marketplace users add (`codex plugin marketplace add yate-ge/GenPet`), while `plugins/genpet/` is the canonical plugin package it exposes. Edit skills, policy, bundled tools, plugin help and manifests directly inside that package. `npm run build:plugin` only regenerates `dist/` and the runtime `package.json`; do not hand-edit those generated files, and do not keep a separate release branch. Keep real user state, private conversations, rejected generations, local reports, and installed dependencies out of Git.

1. Create a short-lived branch such as `feat/growth-qa` from `main`. Work and test there; open a pull request back to `main` when a remote repository exists.
2. Run `npm ci` and `npm run verify:fast` while editing. Edit installable static content only under `plugins/genpet/`. Whenever `src/` or plugin package content changes, run `npm run build:plugin` and commit the resulting `plugins/genpet/dist/` and runtime `package.json` in the same commit; CI rejects stale generated files. Run `npm run verify:release` before merging such changes. It installs the plugin through the repository marketplace in a temporary Codex home and does not touch the real Pet.
3. Review the files to be committed, especially new images and evidence JSON. Keep only examples that can be publicly redistributed and whose provenance is documented.
4. Merge after checks pass. Users following `main` receive the change with `codex plugin marketplace upgrade genpet`. For a release, bump the version in the root `package.json`, root lockfile and `plugins/genpet/.codex-plugin/plugin.json`, rebuild, and tag the commit (for example `v0.2.5`) so users can pin it with `--ref`. Attaching `npm run package:plugin`'s ZIP to the GitHub release is optional, for offline installs.

The `output/` directory is ignored by Git and holds local reports and archives. The installable plugin contains only the bundled runtime, skills, Hatch Pet tools, policy defaults and two help documents. The native Pet, adoption clock, and generated artwork remain in the user's local data directories.

For urgent fixes to an already published version, branch from its tag or use a `release/x.y` maintenance branch only if multiple supported versions need parallel fixes. Routine development does not require a permanent `develop` branch.
