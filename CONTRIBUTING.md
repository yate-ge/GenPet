# Development and release

See [the architecture](docs/ARCHITECTURE.md) for the layers, source map and extension points. `framework/` (prompts, references, skills, debugger-web) is the shared editable source. Keep rules goal-oriented, genes open, and user-context/evolution decisions with Agent. Do not add a closed taxonomy, facial template, activity classifier or numeric growth threshold.

Product rules have a single source: [`framework/prompts/meta.md`](framework/prompts/meta.md). `unit-request` prepends it to every unit, so unit prompts contain only their own steps, results and checkpoints and refer to meta sections by name. When a product rule changes, edit `meta.md` and only those unit checkpoints that depend on it; do not restate the rule in references, READMEs or skills. Prefer positive phrasing in prompts, and keep negative examples in fixtures or saved review cases rather than in prompt text.

`plugins/genpet-dots` and `plugins/genpet` keep only host-specific manifests, config and host-only skills. `npm run build:plugin` regenerates their `dist`, package metadata, shared prompts/references/skills and optional debugger assets. Edit the source, not these generated copies. Native image-processing helpers belong only to ordinary Pet.

Use Node 22+, `npm ci` and `npm run verify:fast` (types, formatting, tests); `npm run format` applies the formatting. For generation, follow [the unit contracts](framework/references/generation-units.md): fix upstream inputs, use `unit-request`, save the generated result, check `verify-unit` and evaluate its meaning separately. When input or result fields change, update the relevant `.md` and `units.json` together; product-rule changes do not require a new schema. Behavioral checks may use independent subagents with synthetic context and saved inputs/outputs. Keep generated test art under ignored `output/`, and report sample limits. Do not mutate the user's Pet, create schedules or install into the user's environment as a test. Use isolated `GENPET_DATA_DIR` and `CODEX_HOME` when integration testing is requested.

Published changes must increment the semantic version consistently across root package/lock metadata and both plugin manifests/runtime packages. Fetch `origin/main` before `npm run verify:release`; never alter its comparison base just to pass a gate. The gate builds and verifies both packages through the official CLI in a temporary home. When a user reserves end-to-end checks for later, keep them pending and do not call the development archive a published release.

`npm run package:plugin` prepares the local marketplace archive. After actual validation and release checks, publish via the project's normal Git/release workflow. Never commit private user context, real pet records or unpublished generated artwork by default. See AGENTS.md for release invariants.
