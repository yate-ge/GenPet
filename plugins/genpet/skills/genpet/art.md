# 图像生成

宠物形象、家和故事物件的真实出图流程。请求的内容由 `units/appearance.md`、`units/home.md`、`units/story-item.md` 形成，看图由 `units/review.md` 做，更新宿主见 `host.md`。

图像任务和独立审核交给子代理，这样源图、候选和预览留在内部。宠物的身体、色块和器官不被改动，所选的 Pet 不变。

## 宿主格式

透明 v2 atlas：1536×2288，8×11 格，每格 192×208。九种动作行的有效格数依次是 6、8、8、4、5、8、6、6、6，最后两行是十六个方向。未用的格透明，r0c6 是中性参考。格式检查通过不等于可爱、阶段、动画或故事成立。

槽位名称不等于必须完成的字面动作；表达和审核按 principles.md「四、宠物长什么样」。`--egg` 的壳动作和中性方向格可以复用。

## 生成一整套

1. 通过 workspace dependencies 找到 Python，读取运行 manifest。`art-request` 的 `.id` 作为 `pipeline-prepare` 的 `requestId` 以及 `accept-art` 的第一个参数，`.contract` 是宿主格式。
2. 用当前 appearance 请求、真实参考和绝对的 run 路径调用 `prepare_pet_run.py`；蛋用 `--egg`，其余按当前的并行模式。不覆盖原 run，重试使用它已保存的工作。
3. **基准图**先实际看图、记录接受（第一道审核）。
4. 基准通过后，九种动作和方向各自独立并行生成，按 manifest 的真实 job ID，不额外串行生成方向参考。方向可以只生成一侧，由处理代码镜像；不对称的身体必须核查关键部件，镜像破坏身份时给那一组单独生成，不盲目翻转。
5. 提取、统一尺寸、透明和组装用确定性脚本；脚本的通过只是格式结果。
6. **整套图**在实际显示大小下视觉审核一次（第二道审核），确认动作、方向、身体和穿戴一致。合计两次视觉审核。
7. 相同的视觉错误第二次换方法。单行达到 helper 的返工上限（初次之外再重画两次）时，用已接受的基准姿势补帧，记录不足，再看组装后的真实结果。
8. 候选、源图、预览、失败记录和运行输出全部保留。

**成长图**可在预兆出现时先准备并接受，记录阶段和引用，到期直接复用；衣装和故事变化仍需匹配。没有有效的目标阶段基准时保持未完成，不拿旧阶段的图宣称成长已完成，也不说成长或显示完成。基准失败时，先复用已接受的、适合目标阶段的图；没有合适的图就保留 pending 和明确的失败证据。宿主恢复后继续上传同一个计划，不重新领养。

## 图像协调者

整套图交给一个图像协调子代理，提供实际的 Pet/cloud ID、operation、request 和目录。每次交接都有等待成本，所以协调者连续推进，只在需要用户或主 Agent 决定时回报。

- **尽量并行。** 开几个执行者由宿主和当时的情况决定，协调者自己也出图。基准审核进行时，就备好各 job 的提示并开好执行者；基准通过后，一次交给每个执行者它那份 job（各自的请求、身体和阶段约束、参考）和基准路径，执行者连续做完，不逐张回报，不等转派。
- **分工。** 执行者只保存自己的源图和回执；共享 manifest、组装、有限修复、Pet 记录和目标更新由协调者处理。独立的 ImageReviewer 只负责基准和整套两道看图关卡，返回结论、观察和修正，不写长报告。终审期间，协调者先备好接受、上传和回读所需的参数。
- **收尾。** 具备宿主接口时，协调者完成接受图保存、同 ID 更新和回读后，直接执行 stories.md 步骤 8 的 `finish-story`，再把最终文件和实际结果交主 Agent 取 `story-output` 并表达。
- **交给执行者的内容**：只给它自己那些 job 的请求、身体与阶段约束、相关参考；不重放完整的报告和历史。依赖前一张的修改，用实际审核过的当前图。每次调用都保存工具给出的原始 PNG，连同路径和哈希。

## 接受与展示

- `accept-art` 的 `portrait` 和 `atlas` 分别接受；场景图是 `scene`，家的画面是 `home`，道具叙事的物件图是 `prop`。新阶段的最终消息用 portrait；整套 atlas 不当聊天图。
- 安装不改用户的选择、不采用新 Pet、不生成图。
