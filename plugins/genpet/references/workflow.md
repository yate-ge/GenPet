# Agent workflow

All CLI output is internal. Load `prompts/output.md` before producing any chat text, including progress messages. Read `prompts/meta.md` for every generation. Framework files may be edited by developers; persisted individual genes remain that individual's identity. Generation uses [structured units](generation-units.md) with separate input/result records; do not collapse all decisions into an uninspectable plan.

Resolve this installed plugin's root from the skill directory (`../..`). Run `node ROOT/dist/cli.js ...`; do not use a developer checkout or another package's runtime. `config/host.json` selects the host. `status` is read-only.

1. Read `status`. If it reports `legacyFile`, follow [migration](storage.md) before adoption. If `pending` exists, resume it, using the saved plan and assets. A completed start resumes the existing pet and can present its latest story; it never creates another identity.
2. For a new invocation use a stable trigger ID (`manual:UUID`, scheduled `due.triggerId`, or an ID supplied by Dots proactive work). Reuse it on retry. `begin-story TRIGGER_ID initialization|story` allocates one pet ID if needed and returns one operation ID and the pet's `growth` (pace ceilings and any change this story must carry; `status` shows it too). A completed trigger returns the existing story. Another unfinished operation must be resumed first.
3. Read `prompts/initialization.md` for a new pet, otherwise `prompts/story.md` and `prompts/evolution.md`. Follow the unit sequence in [generation-units](generation-units.md), reading each unit separately and using its upstream result. New genes record their `designBasis` before any drawing. Generate and save personality once after genes, then use it in every story and state decision. For an old pet lacking personality, form it once from existing genes/history and save it with the next story; reads and installation never backfill it. Agent chooses user context, observation range and evolution judgment. Save brief internal envelopes with `record-step OPERATION_ID UNIT RESULT_FILE`; reuse completed unit results on resume. Review concrete user connection and personality actions in story/state content; the runtime does not judge them by categories or text equality. Assemble StoryPlan from these results, write it to an absolute file and run `plan-story OPERATION_ID PLAN_FILE`. The plan is the story first, followed by its state/appearance decisions. Use the [small record format](storage.md). The saved plan is immutable during artwork retries; do not reroll genes or personality.
4. `art-request` provides the current request ID, chosen stage, genes, story and this pet's accepted `savedArt`; the Agent chooses identity references and any reusable appearance from it. If the planned appearance uses `reuseArtId`, use that same saved file and its acceptance record. For new visuals use the appearance unit's saved request, built-in imagegen and [desktop](desktop.md) or [Dots](dots.md) actual host format. Review the actual returned file with `prompts/image-review.md` in its check order; keep concrete observations, failed candidates and targeted repairs. For each accepted visual or artifact run `accept-art REQUEST_ID ABSOLUTE_FILE KIND PROVENANCE [DESCRIPTION]`. Kinds are storage purposes, not story categories: `portrait`, `atlas`, `avatar`, `story`, `artifact`. Story pictures do not need a transparent background. Files are copied into this pet's persistent assets.
5. If appearance changes, update the bound host target before completion. Desktop: `publish`. Dots: [its own Avatar workflow](dots.md). Preserve the user's current Avatar selection; if the target is active, request its immediate refresh. Do not create a second entry for a state or evolution. Host failures retain the saved plan, references and unfinished result for retry. No appearance change requires no host update.
6. `finish-story OPERATION_ID` commits stage, current state, history, internal generation steps and trigger completion together. Until then the former completed stage/state remains current. `story-output STORY_ID` returns actual saved story media. Compose the output unit using actual completed results and accepted media; its internal result can be recorded with the completed story ID before presentation. Use a suitable completed portrait/Avatar as story art when the story calls for it, or generate dedicated story visuals. Technical results and unit envelopes stay in records, and user-facing output follows `prompts/output.md`.

7. After a completed hatch, handle the one-time user naming invitation through [naming](naming.md). A name reply updates that exact individual without generating another story. Deferred or unanswered naming never blocks scheduled stories.

Imagegen creates pixels; scripts only validate, extract and assemble them. Incomplete generation is not a new adoption. Keep already completed assets when tools fail. Only report display confirmation when actual host evidence exists; delivery of a refresh request is a separate result.

The start command sets up [scheduling](scheduling.md) after the first completed story. Installation alone does not run adoption, imagegen or schedules. Developer tests use an isolated `GENPET_DATA_DIR` and `CODEX_HOME`.
